# Требования: дашборд awf — показывать факты, а не план

Статус: REVIEW
Ревизия: req-6
Входы: dashboard.context.md@ctx-1, dashboard.requirements-review.md@rrv-5, TODO-0357
База кода: e6878c3

## Цель и scope

Один экран отвечает: какая стадия идёт, что сделала, чего ждёт движок, чем
кончилось. Факты берутся из артефактов, о проблеме экран не молчит, старое за
текущее не выдаёт. Основание — запрос владельца 03.11 и
`dashboard.context.md` (CTX1–CTX21); приоритет R — в первой строке его раздела.
R14/R15 отложены. Вне scope: CTX21, MCP-тулы кроме открытия дашборда (R12),
`awf metrics`, очередь забега, `worker_pid`.

## Текущее поведение и ограничения

Дашборд сам считает статус, часть читателей не подключена; детали —
`dashboard.context.md`.

## Требования

### R1 — События не врут и не теряют проблемы

P1. MUST. Источник: CTX2, CTX12.

AC1 — «stage complete» только при `exit=0`; при `exit≠0` событие красное, с
кодом и словом «fail»/«ошибка».
AC2 — события: вердикт `verify-pack` из `verify_facts` при смене, пропуск
чек-листа (`checklist-check: skipped …`), таймаут (`BD-30: supervisor signal
timeout after Ns`), выход движка (AC7), `worker exit` (`Agent stage finished:
<role> (<kind>) for <todo> (exit=N)`), ретрай (`A7: fix_round …`,
`Transition: … action=fix_round`); `Pipeline exited` событием не считается.
AC3 — события старше старта текущего прогона не показываются, шапка его
называет. Граница: `run.yaml.started_at` при `active=true`, иначе время строки
`Pipeline started with N stages:` последнего запуска в `orchestrator.log`
(завершённый `run.yaml` не годится — `awf start` его не очищает). Нет обоих —
событий нет, шапка «граница прогона неизвестна».

### R2 — Сводка юнита показывает цель

P1. MUST. Источник: CTX1.

AC4 — сводка начинается с цели: первый непустой абзац тела TODO. Пропускаются
только ведущий YAML front matter (между первыми `---`; прочие `---` —
содержание) и `<!-- -->`; заголовки до абзаца пропускаются, в теле — граница
абзаца; цитаты `> ` и пункты `- [ ]` — содержание.
AC5 — «Полный текст» — TODO без потери строк, `---` не становится заголовком.

### R3 — Проблема названа причиной

P1. MUST. Источник: CTX6, CTX7.

AC6 — при `Blocked` видны юнит, причина из `outbox/BLOCKED-<id>.md` (первый
абзац) и ссылка на файл.
AC7 — при `Stale`/`Dead` видны rc, сигнал, стадия, TODO и последняя строка
трейсбека из последнего `ENGINE-EXIT-<ts>-<pid>[-n].md` с полем `- todo:`
равным юниту state; нет файла — «файла нет» и путь.

### R4 — Момент решения виден целиком

P1. MUST. Источник: CTX3, CTX4, CTX5, CTX15.

AC8 — баннер verify: вердикт `ok`/`failed`/`nothing-measured`/`error`/
`unreadable`/«файла нет», упавшие секции (`- <секция>: FAIL (rc=…)`), первая
причина; у `unreadable` и «файла нет» свой текст; `status=hidden` — причина по
AC11.
AC9 — ожидание verify: `since`, прошедшее время, дедлайн, причина; таймер идёт
на каждом опросе.
AC10 — статус коммита (`committed`/`skipped`/`refused`/`error`), `reason`; при
`skipped`/`refused` — исключённые файлы из `verify_facts.commit.excluded`
(пары `[путь, причина]`, AC35).
AC11 — видимость пака — один владелец `verify_facts`: пак виден, пока идёт
verify (`current_stage_kind=verify` или `verify_waiting`); вне verify — только
если файл новее `state.updated_at` И
`read_gates_facts(..., tree_sha=<отпечаток>).stale=false`. Причина скрытия —
`pack_hidden_reason` (AC35): `not-current` «пак не собран для текущего прохода»,
`other-tree` «пак от другого дерева», `no-tree-sha` «пак без отпечатка дерева».
Сверка отпечатка кэшируется на процесс на 10 с (сброс при смене HEAD или
`updated_at`).
AC12 — при `checkpoint_pending` видна ссылка `checkpoint_form_url`.

### R5 — Один ответ на «что происходит»

P1. MUST. Источник: §1 контекста, CTX3, CTX9.

AC13 — каждое поле равно ответу владельца на одном состоянии: статус, стадия,
`verify_waiting`, `engine_dead`, `stale_stage`, `pipeline_running` —
`awf_status`; вердикт пака — `verify_facts` (тот же вызов, что AC11); попытка —
`stage_attempts["<todo>:<stage>"]` (движок пишет до запуска), лог даёт только
длительности; при расхождении видно число из state, в подсказке — оба. Проверка
— равенство на фикстурах state и артефактов; бейдж не зелёный при
`engine_dead`/`stale_stage` и не `Dead` при `pipeline_running`.
AC14 — опрос не дорожает: медиана 5 запросов после прогрева, лог ≥ 35 000 строк —
холодный `/api/state` ≤ 2 с, тёплый ≤ 1 с; параллельные склеиваются; сверка
отпечатка — в кэше AC11.
AC35 — контракт `verify_facts` (владелец `brief_sections.py`, второй читатель
запрещён): `status`, `report`, `failed_sections`, `first_failure`, `note`;
`pack_hidden_reason` пустой либо `not-current`/`other-tree`/`no-tree-sha`,
непустой даёт `status=hidden` и текст AC11 с приоритетом: «файла нет» (пустая
причина), `not-current`, `no-tree-sha`, `other-tree`; `commit` —
`{status, reason, excluded, mtime, fresh, from_previous_pass}`: `excluded` —
пары `[путь, причина]`, `mtime` — время аудита, `fresh=false` при аудите старше
`updated_at`, `from_previous_pass=true` при `mtime` раньше `verify_waiting.since`;
`{}` — без `todo_id` в state.
AC36 — пак: ровно шесть документов (context, requirements, requirements-review,
architecture, test-spec, readiness); каждый ≤ 2200 слов (`count_words`), пакет
≤ 11 000; отчёта стадии (`finalize`) в пакете нет.

### R6 — Финал и забег показаны как есть

P2. MUST. Источник: CTX7, CTX16.

AC15 — после выхода движка экран показывает «прогон завершён» с итоговым
статусом, временем и вердиктом последнего прохода; «Pipeline exited» как ошибка
не используется. Файловая страница берёт вердикт из снимка, записанного до
`clear_state` при `current_stage_kind=verify` (пак не скрыт, AC11), иначе
«вердикта нет»; живая вкладка — из последнего `/api/state`, где пак был виден
(AC11), после остановки — «обновление остановлено, снимок от HH:MM:SS», без
пересчёта.
AC16 — чип забега: `position`, `completed`, `stop_reason`, `budget_minutes`,
`budget_left_minutes`, `elapsed_minutes`, `downtime_minutes`, `stall`, ссылка на
`report_file`; при `active=false` — «забег закончен».

### R7 — Свежесть факта видна

P2. MUST. Источник: §9 вопрос 6, CTX5.

AC17 — в шапке один общий штамп «снимок от HH:MM:SS» по времени расчёта.
AC18 — у блока виден возраст и своё правило: пак — AC11, по возрасту не стареет;
коммит — виден, пока идёт verify или `commit.fresh=true` (mtime новее
`updated_at`), возраст по `commit.mtime`; записанный раньше `verify_waiting.since`
подписан «от прошлого прохода» (`from_previous_pass=true`), при `fresh=false` —
«последний известный коммит от HH:MM» (времени и `tree_sha` в файле нет, AC35);
лог — «не обновлялся N мин», «устарел» только при `stale_stage`; забег — окна
нет, `active=false` — «завершён».
AC19 — старый факт не подменяется: без данных блок говорит «нет данных», а не
прошлый юнит.

### R8 — О проблеме сообщает уведомление

P2. MUST. Источник: CTX11.

AC20 — для `Blocked`, `Dead`, `Stale` и финала есть уведомление с одной строкой
причины; повтор не спамит.

### R9 — Видно, кто и что делает

P3. MUST. Источник: CTX9, CTX13, CTX14.

AC21 — рядом с ролью имя стадии; подпись и визуал в сайдбаре, чате и
уведомлениях даёт роль стадии, они совпадают.
AC22 — панель Worker: последняя содержательная строка (не баннер) и дерево
`live_members_of_state(state)` (общий владелец, не второй разбор `/proc`) — pid,
метка, стадия. Баннер — строка по шаблону `^>\s*build\s*·`; содержательная —
последняя непустая не по шаблону, иначе «нет вывода». Осиротевший — член дерева с
`ppid` 1 или вне набора членов (корень — нет), помечен отдельно; плоский
`StatusResult.worker_processes` деревом не считается. Длительность — от старта
процесса (`/proc/<pid>/stat`, поле 22 `starttime` + `btime`), не от стадии; нет
данных — «неизвестна».
AC23 — без живого воркера панель говорит «воркер не запущен», а не показывает
последний чужой pid.

### R10 — Дифф не приписывает юниту чужую работу

P3. MUST. Источник: CTX10.

AC24 — блок изменений называет коммит-базу и число коммитов после неё.
AC25 — если база отстала от HEAD, подпись «всё после базы, не только этот юнит»;
размер не выдан за работу юнита.
AC26 — если контракт юнита перечисляет файлы, показано пересечение с ними.

### R11 — Пустое и битое состояние объяснено

P3. MUST. Источник: §9 вопрос 7, §6 контекста. Укрепление: 500 не воспроизведён;
пустое дерево даёт `idle` без объяснения.

AC27 — без `.agentic`, с пустым `pipeline.yaml`, 0 стадий, без лога и `state`
страница отдаётся и объясняет, чего не хватает, что делать.
AC28 — битый TODO, handoff или `GATES` даёт блок «данные повреждены» и не ломает
остальные блоки и опрос (`read_gates_facts` отличает `unreadable` от
отсутствия). Для `COMMIT-AUDIT` исход один — «аудита коммита нет»:
`read_commit_audit` возвращает `None` и на отсутствующий, и на битый файл.

### R12 — Авто-открытие по одному правилу

P3. MUST. Источник: CTX8, CTX20, запрос владельца.

AC29 — одно правило на все пути (общий `should_open`; исключение — явный вызов
AC31): открываем, если сервер поднят этим запуском, авто-открытий в нём ещё не
было и для URL не было открытия 10 минут. «Поднят этим запуском» — маркер
`state/dashboard_boot` (`pid`, `ts`), пишется при каждом реальном старте, в том
числе на новом порту после занятого; `ts` не старше старта + 5 с. «Реюз» — свой
сервер не стартовал: вкладки нет, причина на экране. «Уже открывали» — маркер
`context/dashboard_opened` (`ts`, `url`, запуск): тот же URL моложе 10 минут —
URL текстом; другой URL, новый запуск или старше 10 минут — можно. Файловой
странице (`file://…/current.html`) boot-маркер не нужен: одна вкладка на URL за
10 минут. Исходы — C8.
AC30 — в CI, под тестами (`PYTEST_CURRENT_TEST`), при `AWF_NO_DASHBOARD_OPEN` и
без `DISPLAY`/`WAYLAND_DISPLAY` вкладка не открывается ни на одном пути
(`gui_available()`).
AC31 — явный `awf dashboard --open` и MCP `awf_open_pipeline_dashboard` открывают
по запросу (окно 60 с каждого пути) и авто-правилом не отменяются, в том числе
при отсутствии или порче boot-маркера; авто-открытие не закрывает и не
переоткрывает вкладку.

### R13 — Документация совпадает с экраном

P3. SHOULD. Источник: CTX18.

AC32 — `USAGE.md`/`USAGE.ru.md` называют фактические вкладки, опрос 3 с и
таймлайн; в `BACKLOG.md` «Модели на карточках чата» и «Agent Chat после передачи
обратно» закрыты, «Авто-открытие при реюзе» переходит в R12.

### R16 — Оценка времени до финиша

P3. MUST. Источник: остаток A20 (коммит `a2bd764`).

AC33 — ETA только как оценка: подпись «оценка по прошлым виткам»,
`stages_done`/`stages_total`, прошедшее время; метод — медиана завершённых
стадий по логу текущего прогона.
AC34 — меньше двух стадий — «оценки нет», а не выдуманное число; ETA не выглядит
фактом и не влияет на статус.

## Сценарии

- C1: `exit=1` → красное событие (AC1, AC7).
- C2: `verify_waiting` → вердикт, секции, таймер, коммит (AC8–AC12).
- C3: выход движка → «прогон завершён» (R6).
- C4: пустой проект → причина и шаг (R11).
- C5: две стадии одной роли — по имени (R9).
- C6: сводка начинается с цели (AC4, AC5).
- C7: старое не выглядит текущим (AC18, AC19).
- C8: авто-открытие — десять исходов (AC29–AC31, T18).
- C9: экран равен `awf_status` и `verify_facts` (AC13).
- C10: видимость пака — один владелец (AC11, AC35).
- C11: граница событий — строка лога (AC3).
- C12: вкладка после выхода — снимок (AC15).

## Не должно измениться

INV1 — экранирование: TODO и handoff — текст LLM; `html.escape`, markdown,
нейтрализация `href`, JSON в `<script>` без `<`.
INV2 — `/api/state` без `Access-Control-Allow-Origin`; отчёт забега — только по
имени из строгого шаблона и внутри `outbox`.
INV3 — запись HTML атомарная; испорченный TODO/handoff не даёт 500.
INV4 — опрос: один запрос в полёте, следующий после ответа, период 3 с.
INV5 — контракт шаблона: поле из `/api/state` читается шаблоном.
INV6 — чтение не меняет `current.yaml`, `run.yaml` и артефакты юнита.
INV7 — целевые тесты зелёные (84 passed на базе): `test_dashboard.py`,
`test_dashboard_open.py`, `test_dashboard_snapshot.py`.
INV8 — `generate_state_dict` не падает и не висит без `.agentic`; снимок
JSON-сериализуем.
INV9 — одна авто-вкладка за запуск и одна на URL за 10 минут
(`state/dashboard_boot`, `context/dashboard_opened`, AC29, C8).
INV10 — сверка отпечатка не меняет индекс и дерево: тот же
`git_utils.tree_fingerprint` без `git stash`/`add`; кэш только в памяти.
