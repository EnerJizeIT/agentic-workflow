## Цель и scope

Цель — сократить вход без потери качества: промпт растёт, повтор стартует с нуля.

В итерации: диета (R1), пакет и вложение (R2–R5), сессия и дельта (R6–R9).

Вне: переписывание промпта, смена ролей и прав, история вне `opencode.db`, миграция 1.x → 2.x.

## Текущее поведение и ограничения

- Спавн — `awf/agent_stage.py::run_agent_stage`: `opencode run` `--agent`, `--title awf-<role>-<todo>`, вложения, `--model`; `--session` нет (CTX2).
- Промпт — `awf/supervisor.py::build_prompt` (`:176-181`): `Prior completed TODOs:` из всех `.agentic/done/` — 297 id, 3 288 из 5 654 символов (CTX5).
- Вложения: роль 15.3–16.2 КБ, доктрина 2 958 Б, TODO 2 939 Б, handoff 3.6–4.1 КБ; у аудитора 7 файлов (CTX4).
- Повтор стадии — не сущность: отказ дописывает `## REVIEW-фикс` (`awf/api/hygiene.py:1205`), движок возвращает юнит автору; у TODO-0296 — 6 секций, 4 сессии (CTX3).
- Id сессии не пишется (CTX9); метрики ищут по заголовку (`awf/metrics.py:120`; CTX8). `agent-qa-review` и `agent-project-auditor` — readonly без `edit`/`write`; полный сьют >300 с.

## Требования

### R1 — Список завершённых юнитов в промпте не растёт с историей

MUST, в итерации. Источник: 0250 п.1; CTX5.

Поведение: промпт называет восемь последних завершённых юнитов и подсказку к полному списку; полное перечисление не выводится.

Критерии:
AC1 — ровно восемь последних `TODO-NNNN` при архиве ≥ 8, при меньшем — все (текущий юнит не считается); самый ранний не назван.
AC2 — подсказка называет `awf report` и путь `.agentic/done/`.
AC3 — при 1000 юнитов фрагмент ≤ 300 символов и не зависит от размера архива.
AC4 — блоки «Pipeline context», «Stage assignment», «Stage identity» на местах.

Сценарий: C1.

### R2 — Детерминированный пакет контекста стадии

MUST, в итерации. Источник: 0250 п.2–3; CTX4.

Поведение: до спавна формируется `.agentic/context/STAGE-<todo>-<stage>.md` — факты контракта, git и артефактов без модели; те же входы дают те же байты.

Состав: (1) задача и роль; (2) контракт: требования, границы, чек-лист, приёмка; (3) состояние: baseline sha, изменения git, diffstat, untracked; (4) handoff прошлой стадии (до 20 строк) и путь; (5) при `## REVIEW-фикс` — дословное тело секций TODO, красные тесты, хвост падения; (6) ссылки: дизайн/`source_ref`, карта поверхностей, тесты; (7) «как работать»; (8) sha входов.

Обрезка: 3, 4, 6 — в ссылки; 1 и 7 — до 10 и 12 строк, излишек — «сокращено» со ссылкой. 150 строк — потолок секций 1, 3, 4, 6, 7; 2, 5, 8 не режутся и не считаются (решение супервизора, RR33). Тело секции отдаёт новый helper в `awf/todos.py` на границе `_apply_section_update` (`awf/api/hygiene.py`); `review_headings` — только заголовки.

Критерии:
AC5 — файл по пути R2, восемь секций в порядке; секция 5 несёт дословный текст всех `## REVIEW-фикс` — находки и следствия, не заголовки; при продолжении — девятая (R9).
AC6 — две сборки на тех же входах совпадают побайтово.
AC7 — сумма строк секций 1, 3, 4, 6, 7 и 9 ≤ 150 при длинном diff, handoff и дельте; излишек — в ссылки.
AC8 — нет секретов и переменных окружения; источники — контракт, git, outbox DONE, handoff, stage-log, `.agentic/context/`.
AC9 — нет входа секций 2, 4, 6 — «n/a», стадия не падает; секция 5: тело `## REVIEW-фикс` из TODO, красные тесты из `awf verify-pack`, хвост из stage-log; нет — «n/a».
AC41 — фикстура: контракт 169 строк и шесть секций `## REVIEW-фикс` несутся целиком, пакет длиннее 150 (AC7 — только секции 1/3/4/6/7).

Сценарии: C1, C2.

### R3 — Свежесть пакета и его подчинённость фактам

MUST, в итерации. Источник: 0250 п.4.

Поведение: пакет хранит sha входов: TODO, baseline, роль, доктрина, handoff; живой tree-sha не вход — стадия меняет дерево. Секция `stage_context` (`awf verify-pack`, `GATES-<todo>.md`) пересчитывает sha; расхождение или отсутствие файла при `on` — провал с текстом «regenerate with awf context-pack».

Критерии:
AC10 — при `on` `stage_context` (`awf verify-pack`): «актуален» либо «устарел» с перечнем изменившихся входов; «устарел» — провал.
AC11 — при `on` изменение любого входа даёт «устарел» и команду пересборки; совпадение — «актуален» и прежний вердикт.
AC12 — отсутствие файла при `on` — «устарел» и провал, не пустой раздел; при `off` — «выключен», вердикт прежний.
AC13 — пакет назван только в `stage_context`; вердикт и проверки его не называют.
AC36 — в пакете есть строка «проверяй утверждения пробами».

Сценарий: C2.

### R4 — Пакет вкладывается в стадию, сбой сборки не валит стадию

MUST, в итерации. Источник: 0250 п.5.

Поведение: спавн добавляет `--file <пакет>` после TODO и до handoffs; handoffs не меняются; нет файла — собирается до спавна; ошибка сборки — предупреждение в stage-log, спавн без пакета. R4 гарантирует старт и код возврата, не вердикт: при `on` отсутствие пакета проваливает вердикт по AC12.

Критерии:
AC14 — argv содержит пакет; порядок: роль, доктрина, TODO, пакет, handoffs без изменений.
AC15 — при отсутствующем файле пакет собирается до спавна.
AC16 — при ошибке сборки стадия стартует без пакета, причина в stage-log, код возврата тот же.
AC17 — при `context_pack: off` и `reuse_session: off` флаги, порядок и `--file` прежние (промпт по R1 не сравнивается); при `on` и `reuse_session: off` — только `--file <пакет>`.

Сценарии: C1, C2.

### R5 — Команда сборки пакета

MUST, в итерации. Источник: 0250 п.6.

Поведение: `awf context-pack <todo> --stage <name> [--stdout]` собирает пакет; `--stdout` печатает пакет и не пишет файл.

Критерии:
AC18 — без `--stdout` пишет файл по пути R2, код 0; повтор байты не меняет.
AC19 — `--stdout` печатает содержимое пакета, файл не создаёт и не меняет.
AC20 — неизвестный TODO или стадия дают ненулевой код и сообщение с именем значения; файл не создаётся.

### R6 — Идентификатор сессии сохраняется

MUST, в итерации. Источник: 0251 п.1; CTX8, CTX9.

Поведение: при `reuse_session != off` заголовок получает стадию и суффикс попытки `awf-<role>-<stage>-<todo>-a<N>` — ключ уникален по паре (юнит, стадия); при `off` — прежний `awf-<role>-<todo>`. Свежий спавн ищет сессию по точному `title` и окну `time_created` от старта спавна; `directory` не фильтр, только тай-брейк (замер: `$HOME` у 95% сессий `awf-*`). На продолжении id берётся из файла пары и проверяется в базе. Файл `.agentic/context/SESSION-<todo>-<stage>.json` несёт `session_id`, `title`, `agent`, `model`, `attempt`, `ts`. `attempt` — счётчик пары: прибавляется до спавна, не откатывается при смерти, переживает откат и `awf continue`; первая попытка — 1. Недоступная база, незнакомая схема, ненайденная сессия — id не пишется, причина в stage-log, стадия не падает; на продолжении прежний файл пары остаётся.

Критерии:
AC21 — при `reuse_session != off` после стадии файл есть, шесть полей; `attempt` равен зарезервированному номеру входа пары, после отката — 2; при продолжении `session_id` совпадает с id файла пары.
AC22 — недоступная или незнакомая база: на свежем спавне файла нет, на продолжении прежний файл пары остаётся без нового id; причина в stage-log, стадия завершается сигналом.
AC23 — чтение базы под таймаутом 1 с; по истечении id не пишется, код и сигнал прежние.
AC37 — на фейковой базе v1 и v2 захват находит сессию по `title` и окну `time_created`; запись с `directory=$HOME` в окне берётся, та же `title` старше окна — нет; две стадии одной роли получают разные заголовки.
AC38 — метрики находят сессии с `-a<N>` и без; суффикс и стадия не дробят строку роли, статистика не делится.
AC39 — при `reuse_session: off` заголовок без суффикса, база не читается, файл не создаётся.
AC40 — спавн, убитый до захвата, сдвигает счётчик: следующий вход пары получает `-a2` и `attempt: 2`, файла прошлой попытки нет.

Сценарий: C3.

### R7 — Политика продолжения сессии

MUST, в итерации. Источник: 0251 п.2–3; A4, A8.

Поведение: `engine.reuse_session` — `off`, `fix-only`, `always` (алиас `on` = `fix-only`); по умолчанию `off`. `fix-only` продолжает только при повторе стадии (`attempt > 1` пары по R6), независимо от `## REVIEW-фикс`. `always` — без порога: живой файл пары с той же ролью и моделью, в том числе при потерянном счётчике; без файла равен `fix-only`. Разрешены `agent-implementer`, `agent-refactoring-specialist` и `agent-qa-review`; остальные, включая `agent-project-auditor` и супервизора, — свежие.

Продолжение требует совпадения роли, модели и возраста ≤ `engine.session_max_age_minutes` (240) от `ts`.

Критерии:
AC24 — при `off` argv и выбор сессии прежние; новые строки stage-log и отчёта по AC30–AC31 допустимы.
AC25 — при `fix-only` первая попытка без `--session`, повторный вход пары после отката или `awf continue` — с `--session <id>`.
AC26 — при `always` роли вне списка идут без `--session`; сессия другой стадии или другого юнита не берётся.
AC27 — расхождение роли или модели, возраст больше лимита, отсутствие или будущность `ts`, нет файла, нет id или база мертва — свежая сессия и причина.
AC28 — при продолжении остаются `--agent`, `--model` и все прежние `--file`.
AC42 — при `always`, живом файле пары и потерянном счётчике (нет `attempt`) вход пары получает `--session`; при `fix-only` тот же вход идёт свежим.

Сценарии: C3, C4.

### R8 — Отказоустойчивость и наблюдаемость продолжения

MUST, в итерации. Источник: 0251 п.5–6.

Поведение: две неудачи подряд с `--session` (ненулевой код без сигнала либо id не принят) отключают продолжение для юнита до конца; успешная свежая попытка не снимает. Счётчик неудач — ключ по юниту в `state/current.yaml`; переживает `awf continue`, другому юниту не переходит. Продолжение после таймаута или убийства допустимо: id остаётся в файле (0251 п.5).

Критерии:
AC29 — после второй неудачи все следующие витки юнита идут без `--session`, в stage-log строка отключения.
AC30 — в stage-log каждой попытки одна строка `session: reused <id>` или `session: fresh (<причина>)`.
AC31 — `awf status` и RUN-REPORT показывают `reuse: k/n` по стадиям; k/n — продолжения и входы пары (юнит, стадия) из журнала; `off` — `reuse: 0/n`.
AC32 — счётчик неудач юнита переживает `awf continue` и не наследуется другим юнитом.

### R9 — Дельта-контекст при продолжении

MUST, в итерации. Источник: 0251 п.4.

Поведение: при продолжении пакет получает девятую секцию «с прошлого хода»: изменённые файлы, новые `## REVIEW-фикс`, красные тесты; тело секции 5 не повторяет — называет номер витка и отсылает к ней. Входит в общий счёт AC7 (секции 1/3/4/6/7 и 9).

Критерии:
AC33 — на фикстуре с изменённым файлом и новой секцией `## REVIEW-фикс` секция несёт строки про файл и секцию; при пустом диффе и без секции — «нет изменений».
AC34 — при свежей сессии секции нет.
AC35 — в секции строка: прошлая сессия не источник фактов.
AC43 — при новой секции `## REVIEW-фикс` секция 9 называет номер витка, а тело витка есть только в секции 5.

## Сценарии

### C1 — Холодная стадия

Участники: движок, `agent-implementer`; `reuse_session: off`.

1. Промпт: восемь юнитов и подсказка (R1).
2. Пакет собран и проверен (R2).
3. `opencode run`: роль, доктрина, TODO, пакет, handoffs.
4. Стадия пишет сигнал.

Расширения: 2a — готовый пакет; 2b — сборка упала: stage-log, спавн без пакета (R4); 3a — `--session` нет (AC24).

Результат: восемь id, пакет в argv, сигнал.

### C2 — Повтор после отказа

Предусловие: виток отклонён, в TODO есть `## REVIEW-фикс`.

1. Супервизор дописывает секцию и запускает виток.
2. Пакет собран; секция 5 несёт `## REVIEW-фикс` и красные тесты.
3. При `fix-only` — продолжение (R7) и дельта (R9).
4. Стадия пишет сигнал.

Расширения: 2a — красных тестов нет, отметка; 3a — роль или модель не совпали: свежая (AC27); 3b — две неудачи: дальше свежие (AC29); 4a — пакет устарел: провал и пересборка (R3).

Результат: пакет отражает виток, выбор в stage-log.

### C3 — Захват и продолжение

1. Первая попытка без `--session`, заголовок `-a1`.
2. Движок пишет `SESSION-<todo>-<stage>.json` (R6).
3. Повтор сверяет роль, модель, возраст; совпало — `--session <id>`, нет — свежая с причиной.

Расширения: 2a — база недоступна: файла нет, stage-log, стадия не падает (AC22); 3a — id не найден: свежая и предупреждение (AC27).

Результат: шесть полей, выбор объяснён, `reuse: k/n` (AC31).

### C4 — Повтор после таймаута

Предусловие: `fix-only`, файл сессии есть, попытка убита по таймауту.

1. `awf continue` возвращает юнит к стадии; сверка роли, модели, возраста.
2. Совпало — продолжение, нет — свежая.

Результат: продолжение после смерти процесса допустимо (0251 п.5); чужой счётчик не наследуется (AC32).

INV2 — стадия завершается только `DONE-<todo>.ready` или `BLOCKED-<todo>.ready`; молчание — провал.

INV6 — поиск сессий по заголовку префиксный: записи с `-a<N>` и без, стадия не меняет имя роли (AC38).

## Допущения и решения

A1 — устаревание по sha входов (R3), не по живому дереву: стадия меняет дерево; обход TODO ловит дифф-секция отчёта.
A2 — `engine.context_pack: on|off`, по умолчанию `on`; `off` — пакета нет, R3 пишет «выключен», вердикт прежний.
A3 — «фикс-пасс» — признак секции 5, не условие продолжения (R7).
A4 — `off|fix-only|always` и роли из 0251 не сужены; `always` — в паре (A8), отличие от `fix-only` — AC42.
A5 — `reuse: k/n` из журнала пар и файлов сессий.
A6 — Q1, Q2 закрыты: id в `SESSION-<todo>-<stage>.json` (R6), пакет через `--file` (R2–R4).
A7 — R1 при любом `context_pack` (0250 п.1); INV1 сравнивает флаги и вложения, не промпт (RR25).
A8 — `always` ограничен парой `checklist-close`/`checklist-check`, иначе `implementer` попадёт в `checklist-close` (RR26).
