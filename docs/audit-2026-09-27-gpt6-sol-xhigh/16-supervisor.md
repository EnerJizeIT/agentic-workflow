# 16 — Крепость позиции supervisor

**Роль:** независимый аудитор управления. Разделены качество инструкций и техническая возможность worker обойти решение.

## Что работает

`awf/templates/roles/supervisor.md` требует читать handoff, diff и исходники, самостоятельно запускать проверки, сверять факты с первичными файлами, принимать решение и не писать prod-код напрямую. Шаблон QA требует искать опровержения и предъявлять красный тест; implementer обязан подтвердить red-before/green-after. В активном забеге `approve_commit` требует непустой `evidence`; конфликт с reject не публикует APPROVE; commit gate проверяет сохранённый fingerprint, если он есть. Эти механизмы заметно сильнее первоначального «поверь DONE».

## Открытые границы

1. **V-03: источник approval не удостоверяется.** `server.py` регистрирует все 47 tools без профиля роли. `awf_approve`/`api.approve_commit` не получают идентичность caller. В контролируемом активном забеге вызов с `evidence='probe'` и пустым `verified_sha` создал `APPROVE-TODO-0001.ready`. Строка evidence — заявление вызывающего, не доказательство фактического запуска команд. Worker, который может вызвать общий MCP или писать сигналы через shell, способен предъявить решение от имени supervisor. Это P1 относительно обещания независимой приёмки.
2. **V-04: `readonly_roles` не делает reviewer read-only.** В `awf/_env.py` список пуст по умолчанию. Для включённой роли код лишь не добавляет новые `edit/write` override, сохраняя значения пользовательского `opencode.json`; `bash` всегда `allow`. Синтетический config с уже разрешёнными `edit/write` дал reviewer `edit=allow, write=allow, bash=allow`. Тесты текущей волны проверяют только отсутствие новых ключей при пустом пользовательском config. Кроме того, QA шаблон одновременно предлагает писать красные тесты и называет роль read-only — права для этого действия не определены.
3. **Инструкции противоречат друг другу.** Полный `supervisor.md` и `phase-verify.md` требуют независимо запускать verify-команды, но компактный `_core.md`, который `get_phase_prompt` добавляет к каждой фазе, содержит «do not run tests manually». В verify фазе модель получает оба текста. Это снижает надёжность именно независимой проверки.
4. **Контракт качества опционален.** TODO без `verify/prove_red` допустим, `verified_sha` у approve необязателен. В этом режиме gate защищает от ряда гонок, но не удостоверяет, что коммит совпадает с содержимым, которое supervisor реально проверил.

## Практический порядок усиления

1. Устранить противоречие compact/full шаблонов и формально определить, может ли QA записывать только тесты. Проверять результирующий prompt, а не отдельные файлы шаблонов.
2. Разделить набор выдаваемых MCP tools по роли и фазе. Worker/QA не должны видеть approve, reset, rollback, kill и операции завершения забега.
3. Сделать approval переходом доверенного владельца: привязать к поколению забега, fingerprint и commit plan; не принимать одно лишь self-reported evidence как подтверждение проверки. При отсутствии обязательного доказательства возвращать явный отказ.
4. Если требуется строгая гарантия от ошибочного/самовольного worker с shell, изолировать его процесс и права на `.agentic`/Git. При общем пользователе и `bash=allow` prompt и MCP-фильтр уменьшают случайные ошибки, но не являются запретом записи.

**Вывод:** supervisor как метод ревью сформулирован хорошо; как техническая граница полномочий он сейчас недостаточно силён для заявленной независимой приёмки.
