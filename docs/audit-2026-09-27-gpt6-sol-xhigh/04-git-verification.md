# 04 — Git, решение и коммит

**Роль:** инженер Git и независимой проверки. **Проверка:** A-01/A-04/A-09/A-15.

**A-01:** коммит идёт через временный `GIT_INDEX_FILE`; тесты проверяют сохранность чужого staged index и при успехе, и при ошибке hook (`awf/commit_gate.py`, `test_audit25_a01_index.py`). **A-04:** `approve` после записанного reject не публикует разрешающий сигнал; gate повторно сверяет verdict (`awf/api/pipeline.py`, `awf/commit_plan.py`, `test_audit25_a04_verdict_signal.py`). **A-09:** отпечаток учитывает байты untracked и binary tracked файлов (`awf/git_utils.py`, `test_audit25_a09_fingerprint.py`). **A-15:** перед коммитом сверяется сохранённый отпечаток, если он передан в approve (`awf/commit_plan.py`, `test_audit25_a15_verified_sha.py`). Эти тесты прошли в общем прогоне.

Граница гарантии: `verified_sha` остаётся необязательным. `approve_commit(..., verified_sha="")` в активном забеге разрешён, а `fingerprint_refusal` пропускает пустое ожидаемое значение; это закреплено тестом `test_no_verified_file_legacy_behavior`. Следовательно формулировка «коммитится ровно проверенное дерево» верна только для циклов, которые действительно сохранили fingerprint. `CommitPlan` строится у commit gate, а не атомарно вместе с решением; отдельное рабочее дерево из архитектурного предложения не реализовано.

**Вывод:** исходные A-пункты защищены проверками; приёмка пока зависит от дисциплины supervisor передавать `verified_sha` и от отсутствия записи между проверкой и staging.
