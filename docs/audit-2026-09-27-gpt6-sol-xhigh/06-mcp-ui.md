# 06 — MCP, формы и интерфейс

**Роль:** инженер интерфейса и асинхронности. **Проверка:** A-05/A-16/A-20.

**A-05:** форма хранит `received → applied/failed`, записывает результат применения и допускает повтор применения сохранённого payload после сбоя; `read_submit` возвращает статус (`agent_workflow_ui/.../http_endpoint.py`, `test_audit25_a05_form_apply.py`). **A-16:** проверяемый шаблон project-setup больше не вставляет данные модели/скилла напрямую в `innerHTML`; адресный тест прошёл (`test_audit25_a16_innerhtml.py`). **A-20:** блокирующий dispatch и другие вызовы API выполняются через `asyncio.to_thread`/общий адаптер; тест конкурентности MCP вызовов и AST проверка обёрток прошли (`test_audit25_a20_async.py`, `test_audit25_r06_registry.py`).

Реестр MCP действительно един и совпадает с сервером, но выдача инструментов не ограничена ролью: сервер регистрирует все 47 сразу. Это не регрессия A-05/A-20, а отдельная архитектурная задача [профилей tools](15-tools.md). Два HTTP сервера и `tools/awf.py` на 2306 строк остаются местами сложного сопровождения.

**Вывод:** исходные A-05/A-16/A-20 подтверждены; разделение прав MCP открыто.
