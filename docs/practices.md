# Практики, рождённые из инцидентов

Здесь лежат практики, которые проект уже enforcement-ит кодом или воротами.
Формат: практика → инцидент → где усилена.

## Канонический полный сьют + флейк-проба

**Практика.** Полный `pytest tests/` — один канонический прогон на attempt,
привязанный к паре (tree-sha, команда): `scripts/suite-canonical.sh`. Артефакт
`.agentic/context/SUITE-<tree-sha>-<cmd8>.json` хранит sha, команду, старт/конец,
код возврата, счётчики и хвост вывода. Пока дерево не изменилось, повторный
вызов отдаёт артефакт и не запускает тесты; перезапуск — только `--force`.
Свои целевые и контрактные прогоны роль делает сама, а `scripts/run-all.sh`
целиком гоняет только при сомнении в воротах. Контрактные тесты в
`awf verify-pack` при этом: тест-подобные команды (`pytest` / `py.test` /
`python -m pytest`, в том числе через `uv run` / `poetry run` / `env` и после
оператора `;`/`&&`/`|`) выполняются дважды — одинаковый исход даёт `flake: ok
(2/2)`, разный — `flake: unstable` и предупреждение в отчёте. Гейт решает
первый прогон: pass → fail остаётся зелёным с предупреждением, fail → pass
остаётся красным (красное не прячется). Тяжёлые ворота (`run-all`,
coverage, mutation smoke, произвольный shell) и timeout прогоняются один
раз; `flake: off` в контракте выключает пробу целиком.

**Инцидент.** В забеге R2 роли запускали полный сьют примерно 66 раз
(около 9 минут на прогон) — это была доминирующая цена каждого витка:
архитектор и аудитор дополнительно гоняли `run-all` целиком. Второй случай —
тайминговый флейк T1b в `tests/negative/test_roadmap_r1_cancel.py`: одиночные
прогоны файла проходили, а в общем прогоне тест падал, и виток ушёл на
разбор нестабильности вместо работы.

**Где усилена.**
- `scripts/suite-canonical.sh` — кэш по tree-sha, `--force`, артефакт с
  фактами.
- `tests/negative/test_miniwave_m1_suite.py` — кэш, смена дерева, флейк-проба.
- `awf/verify_pack.py` (`FLAKE_RUNS`, секция `contract_tests`) — двойной
  прогон и метка `flake`.
- `.agentic/roles/agent-{implementer,architect-review,qa-review,project-auditor}.md`
  — правило «один канонический прогон на attempt»; materialization
  (`awf/api/roles.py`) добавляет его блоком `awf-suite-canon` каждой
  skill-sourced роли. Источник шаблонов один — пакет `awf/templates/`;
  корневой `templates/` — симлинк на него (нужен dogfood-запуску).
- `tests/unit/test_template_sync.py` — источник шаблонов и живой
  `scripts/suite-canonical.sh` не расходятся с тем, что получает новый проект.

## Сигналы только в свою группу процессов

**Практика.** Убивая дерево процессов воркера, проверяй `proc.pid > 1`:
`os.killpg(1, sig)` — это `kill(-1, sig)`, сигнал всей пользовательской
сессии. Guard в `awf/_proc.py` и tripwire в `tests/conftest.py` неприкосновенны;
перед полным прогоном — green-light grep по обоим маркерам.

**Инцидент.** 2026-09-20 фейк-процесс с pid=1 плюс hard timeout полного
`pytest` трижды убили графическую сессию владельца.

**Где усилена.**
- `awf/_proc.py::kill_process_tree` — guard `pid > 1`.
- `tests/conftest.py` — `_forbid_session_kill` для `os.kill`/`os.killpg`.
- `awf/templates/doctrine/01-process-group.md` — доктрина нового проекта.

## Дерево воркера не откатывать

**Практика.** Не делать `git checkout`/`git stash` на пачку файлов: в
рабочем дереве может лежать чужая незакоммиченная работа. Правильное
действие после сбоя — точечная правка вперёд или сверка diff с эталоном.

**Инцидент.** Рефлекс «восстановить всё из бэкапа» после упавшего стейджа
стирал WIP воркера, который ещё не был проверен.

**Где усилена.**
- `awf/templates/doctrine/02-worker-tree.md` — доктрина.
- Роли-шаблоны: запрет `git checkout/stash` в разделе безопасности.

## Отказ при одновременном запуске — noop с текстом

**Практика.** Два одновременных запуска дают ровно один живой пайплайн;
второй получает `run_mode="noop"` и текст «another launch is already in
progress», а не исключение. Окно «живость → спавн» закрывает lease,
stale определяется по живости процесса, а не по возрасту файла.

**Инцидент.** Гонка `start`/`continue` (и MCP, и CLI) поднимала два
пайплайна на один проект; исключение в отказе выглядело как сбой вызова.

**Где усилена.**
- `awf/api/_lease.py`, `awf/api/_interlock.py` — lease и noop-ответ.
- `tests/negative/test_audit25_a02_lease.py` — парные запуски.
- `awf/templates/doctrine/03-launch-lease.md` — доктрина.

## Таблица поверхностей для инварианта

**Практика.** Для изменений класса «байты/пути/идентичность/замки»
инвариант доставлен только с таблицей «поверхность × исход»: каждый
писатель, читатель и ветка — переведено, исключено с причиной или явный
отказ. Implementer кладёт таблицу в DONE, architect-review ищет соседние
поверхности, QA спускается в клетки, аудитор сверяет с деревом.

**Инцидент.** Юнит закрывал один писатель и забывал второй (logs/dispatch,
manifest/changes, reset/force-init) — инвариант держался не везде и
возвращался багом в следующем витке.

**Где усилена.**
- Материализация ролей (`awf/api/roles.py`) — блок дисциплины у каждой
  skill-sourced роли.
- Пресет `office` — тот же блок у всех ролей офиса.

## Правило остановки и адрес у каждого остатка

**Практика.** Последний пасс ревью объявляется до старта; после него
приёмка без новых HIGH. REVIEW-фикс — одна причина и явная приёмка.
Каждый остаток получает адрес: новый TODO, бэклог или «отклонено» с
причиной.

**Инцидент.** Ревью открывало виток за витком без объявленного дна; часть
находок терялась между витками, потому что у них не было адреса.

**Где усилена.**
- `awf/templates/roles/supervisor.md` — каноны 10.1–10.4.
- `agent_workflow_ui` tools `awf_review_append` / `awf_run_status`.

## Краснота теста до фикса (prove-red)

**Практика.** Регрессионный тест объявляется в контракте юнита
(`prove_red`), сначала показывается красным на baseline, затем зелёным
после фикса. Тест, который не падал до изменения, ничего не доказывает.

**Инцидент.** «Зелёные» тесты, написанные после фикса, проходили и на
старом коде — регрессия оставалась незамеченной.

**Где усилена.**
- `awf prove-red` / MCP `awf_prove_red` — прогон в baseline-worktree.
- `docs/unit-contract.md` — поле `prove_red`.
