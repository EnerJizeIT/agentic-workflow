# Слой 3 — оркестрация, стадии и процессы

**Роль:** инженер исполнения. Просмотрены запуск `awf start/continue`, PID и liveness, цикл оркестратора, сигналы стадий, переходы, ожидание subprocess и остановка дерева процессов.

## A-02 · P1 · У проекта нет атомарного права на запуск пайплайна

При запуске в фоне проверка живости в [start_pipeline](../../awf/api/pipeline.py#L886) отделена от создания процесса и [записи PID файла](../../awf/api/_background.py#L96). Два параллельных вызова могут пройти проверку и создать два пайплайна на одном проекте; поздняя запись перезапишет PID первого. Кроме того, отказ при обнаружении живого PID применяется только при `background=True` ([условие](../../awf/api/pipeline.py#L887)). Обычный CLI использует **foreground по умолчанию** ([cmd_start.py](../../awf/cmd_start.py#L24)), поэтому повторный foreground запуск не блокируется даже без гонки. Проверка личности PID узнаёт лишь argv с `-m awf start|continue` ([`is_our_argv`](../../awf/api/_liveness.py#L45)); установленный console script `awf = awf.cli:main` таким argv не обладает, так что его foreground процесс может быть невидим и для стороннего запроса живости.

**Последствие:** процессы одновременно пишут `current.yaml`, сигналы, архивы и Git index; один процесс может стать невидимым для `awf kill` и статуса. **Рекомендация:** единый lock/lease проекта на весь срок выполнения, одинаковый для foreground и background; резервировать его до `Popen`, а дочерний процесс должен подтвердить владение. PID файл остаётся наблюдаемостью, не механизмом взаимного исключения.

**Проверка после исправления:** два одновременных background вызова, два foreground вызова и смешанная пара дают ровно один выполняющийся пайплайн без второго worker.

## A-14 · P2 · Отказ коммита агентской стадии не останавливает переход

Допустимая политика `on_approved` включает `commit_and_next` и `commit_and_report` ([pipeline.py](../../awf/pipeline.py#L77)). Для агентской стадии [_handle_next](../../awf/pipeline_engine.py#L276) вызывает `_maybe_commit`, но игнорирует его `False` и возвращает следующий индекс ([строки 288–291](../../awf/pipeline_engine.py#L288)). Вызов из `execute_agent_stage` затем возвращает успешный код ([строка 1200](../../awf/pipeline_engine.py#L1200)). Проверка исключения/timeout есть, проверка штатного `False` отсутствует. В verify стадии возврат `False` уже обрабатывается как отказ ([строка 775](../../awf/pipeline_engine.py#L775)).

**Последствие:** pipeline может сообщить успешный переход и продолжить следующую стадию, хотя коммит, требуемый политикой, не создан. **Рекомендация:** вернуть из `_handle_next` и индекс, и результат коммита; при `False` остановить цикл с ненулевым кодом и сохранить TODO активным.

**Проверка после исправления:** подмена `_maybe_commit` на `False` на execute стадии с `commit_and_next` даёт exit code 1 и не запускает следующую стадию. Существующие тесты проверяют timeout здесь и `False` на verify, но не эту комбинацию.

## Положительные свойства

Для worker subprocess предусмотрены отдельная процессная группа, hard timeout, watchdog тишины, обработка сетевых сбоев и сбор логов. `kill_pipeline` проверяет происхождение PID и пытается остановить дочерние процессы. Это уменьшает риск осиротевших worker, но не заменяет право единственного запуска.

## Ограничение

Окно двойного запуска подтверждено в [слое 12](12-recovery-reliability.md) с подменой реального спавна. Настоящие дочерние процессы в конкурентном сценарии не запускались.
