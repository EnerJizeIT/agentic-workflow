# Roadmap стабилизации — версия супервизора

**Дата:** 2026-09-25, ред. 2. **Автор:** супервизор awf (текущая сессия).
**Основание:** [сводный аудит](README.md), [предложение по развитию](ROADMAP-PROPOSAL.md),
[стабилизация качества](QUALITY-STABILIZATION.md).
**Решения владельца:** модель исполнителя и ревьюера не меняется (25.09).
Компенсация — ролями, пайплайном и механикой awf (раздел 3).

Это не пересказ трёх документов. Ниже — что беру, что меняю и почему, и в
каком порядке исполняю.

## 1. Почему прежний контур пропустил 21 дефект

QA-стадия уже есть (с 19–20 сентября) и работает в отдельной сессии: контекст
автора в неё не перетекает. Свежесть сессии работает — в отчётах QA за
0071–0076 видна добросовестная независимая проверка: свой прогон
«красный-до/зелёный-после» (файл заменён на версию из HEAD → 16 failed,
возвращён → 176 passed), сверка sha256, прямые SQL-запросы к базе, проверка
минимальности.

Не хватило не свежести, а **покрытия атак**:

- чек-лист роли покрывал diff, минимальность, red-green и приёмку; все 21
  находка аудита лежат на переходах (check → write, spawn → PID,
  approve → commit), которых в чек-листе не было;
- та же модель не придумывает проверки за пределами чек-листа: веса те же,
  словарь атак тот же;
- роль разрешала «починить самому» — это подталкивает к наведению порядка
  вместо опровержения;
- мой ритуал приёмки (tree-sha, тесты, diff) тоже не про переходы.

Вывод: независимость контекста необходима, но недостаточна. Модель
фиксирована — добавляем полноту проверок и ворота, не зависящие от модели.

## 2. Принципы (по ним принимаю каждое решение)

1. **Доказательство вместо отчёта.** Для дефекта — `prove_red` (тест, красный
   на baseline-снимке юнита и зелёный после фикса). `DONE.json` — указатель на
   факты, не доказательство.
2. **Покрытие вместо силы модели.** Список атак и проверок проектирует
   сильная модель контура; исполняет любая; проверяемое механикой не зависит
   от модели вовсе.
3. **Ворота вместо внимания.** Моё внимание — конечный ресурс и деградирует в
   длинном забеге; всё механическое не должно от него зависеть.
4. **Один юнит — один инвариант или переход.** Главное не размер diff, а
   сколько контрактов и побочных эффектов он трогает.
5. **Раннер не меняется под ногами.** См. раздел 4.
6. **Метрики процесса, не выработки.** Дефекты после приёмки, повторные
   правки, неожиданные файлы, пропущенные негативные сценарии.
7. **Релизное правило.** Открытый P1 на пути TODO → run → verify → approve →
   commit блокирует релиз. Для P2 нужно твоё явное решение с описанием
   обходного поведения.

## 3. Компенсация без смены модели

Четыре рычага, по убыванию надёжности.

1. **Детерминированные ворота — главный.** Всё, что превращается в проверку,
   перестаёт зависеть от модели:
   - `prove_red` обязателен для фикса (механика уже есть);
   - сценарии из таблицы раздела 6 исполняет CI, а не память ревьюера;
   - mutation smoke (`awf mutations`) на критических модулях: выжившая
     мутация = слабый тест;
   - stateful-тест жизненного цикла TODO (Hypothesis, идея из
     QUALITY-STABILIZATION §4);
   - сценарный shim opencode (NEG слой 4 из BACKLOG): фальшивый воркер,
     который пишет сигналы, падает, висит — проверка контура без модели.
   Разум вкладывается в проверку один раз, дальше она ловит всегда.
2. **Сценарий и инвариант пишу я.** В TODO — точный инвариант, точный
   сценарий отказа, ожидаемый красный тест, разрешённые файлы (Mode B/C из
   supervisor.md). Слабой модели остаётся исполнение против спеки, а не
   проектирование проверок. Моё внимание переезжает со сплошной вычитки
   диффов на проектирование атак — один раз на юнит.
3. **Ревьюер: протокол вместо «посмотри внимательно».** Та же модель, свежая
   сессия, но:
   - шесть вопросов (раздел 6) и таблица сценариев — обязательные пункты
     отчёта, не свободное ревью;
   - каждое утверждение DONE и handoff проверяется командой с выводом;
     «подтверждено» без вывода не принимается;
   - прод-код не правится: находка — это красный тест; фикс идёт следующим
     проходом через REVIEW;
   - источник истины — raw diff против baseline, а не пересказ автора.
   Опыт 0071–0076: заданный чек-лист эта модель исполняет добросовестно.
   Значит, рычаг — полнота чек-листа.
4. **Узкие проходы вместо одного широкого — по данным.** Если один проход
   слеп: 2–3 фокусных прохода отдельными стадиями (границы файлов;
   сохранность при отказе; негативные сценарии). Слабые модели на узком
   задании точнее. Заранее не включаю — решаю по пилоту.

Чего не компенсируем: класс ошибки, которого нет ни в одном сценарии, может
пройти первым — гейты догоняют на один инцидент. Глубокие дизайн-решения
слабая модель не рождает — их держу контрактами, границами файлов и волнами.
Поэтому каждый инцидент и аудит закрывается новым гейтом, а не просьбой
стараться.

## 4. Самоподхват: как править awf и не сломать awf

Разведка 25.09: движок спавнится из `awf/api/_background.py:73`
(`sys.executable -m awf`) с `cwd=project_dir`; оба пакета стоят editable из
рабочего дерева; воркерские сессии поднимают MCP-сервер
`python3 -m agent_workflow_ui` из глобального конфига
(`~/.config/opencode/opencode.json:111-119`). Ключевая находка вычитки:
`python -m` ставит **текущий каталог первым в `sys.path`** — в репозитории
awf движок всегда импортирует рабочее дерево, поэтому одной «закреплённой
установки пакетов» мало.

Механизм:

1. **Юнит 0 — пин раннера.** Ключ `automation.runner_dir` в
   `.agentic/config.yaml`: если задан, фоновый спавн запускает ребёнка с
   `cwd=` этот каталог (в нём — закреплённый чекаут awf), иначе `cwd=`
   `project_dir`, как сейчас. `--project-dir` уже приходит абсолютным
   (`awf/api/pipeline.py:858`), argv и опознание PID не меняются, liveness
   работает как раньше. Проверка на входе: каталог существует и содержит
   `awf/__init__.py`, иначе внятная ошибка запуска. Ключ покрывает `start` и
   `continue` (обе точки спавна) и `run_next` (идёт через `start_pipeline`).
   Проверка юнита: тест argv/cwd + тест ошибки + живой smoke (фоновый запуск
   на черновом проекте, затем kill).
2. **Закреплённая копия.** После приёмки юнита 0 — `git clone` репозитория в
   `Desktop/PET PROJECTS/agentic-workflow-runner` и `checkout` нужного
   коммита. Установка не нужна: интерпретатор тот же (системный python с
   зависимостями), код берётся из каталога копии. Бамб —
   `git fetch <dev> stabilization` + `checkout`; откат — `checkout` прежнего
   коммита.
3. **Три слоя изоляции:**
   - **движок** — закреплённый раннер: правки волны исполняются тестами,
     живыми становятся после бамба;
   - **моя сессия супервизора** — перезапуск на границах волн: новый
     MCP-сервер поднимает принятый код. В волне 1 до перезапуска запуск
     юнитов шёл свежим процессом (`run_next`/`continue` из рабочего дерева) —
     так новый `_background` видел пин без перезапуска; после перезапуска
     MCP-инструменты снова основные;
   - **воркерский плагин** — сессии читают рабочее дерево; волна, правящая
     `agent_workflow_ui` всерьёз (не докстринг), требует перед стартом
     перевести MCP-сессии на закреплённый каталог (проектный конфиг, diff
     покажу).
4. **Правило волны.** Коммиты юнитов делает старый (закреплённый) раннер;
   новый код живёт в дереве и тестах; после твоей приёмки — бамб и
   перезапуск сессии.
5. **Git.** Ветка `stabilization` от `0a6554f`, тег `stabilization-start`;
   первый коммит — документы аудита и этот план. Возврат — тег, baseline
   юнитов, обычный git; откат раннера — один `checkout`.
6. **Чистое дерево перед забегом.** В git index ничего не висит (сейчас
   чисто, кроме untracked-папки аудита): старый гейт волны 1 не должен
   тащить чужое. Стейджит только гейт, воркеры — никогда.

## 6. Процесс юнита (обязательный)

1. **Постановка (я).** TODO: один наблюдаемый результат, разрешённые файлы,
   инвариант «до/после», состояние при отказе и повторе, публичные входы
   CLI/API/MCP, блоки `verify`, `gates`, `prove_red`, точный сценарий отказа,
   условие остановки («нужно менять соседний протокол или заметно больше
   файлов — BLOCKED, scope не расширять»).
2. **Исполнитель (`vllm/llm`).** Минимальная правка плюс регрессионный тест.
   Без `git commit`.
3. **Ревьюер (та же модель, свежая сессия, протокол §3.3).** Читает diff,
   контракт и baseline; пытается сломать: другим порядком вызовов, ошибкой
   между записями, чужими файлами, повтором операции. Отвечает на шесть
   вопросов: изменился ли один заявленный контракт; нет ли второго парсера,
   статуса или guard; что будет после ошибки между чтением и записью;
   затронуты ли чужие файлы, git index, архив; тест проверяет публичный исход
   или mock; что можно удалить без потери поведения. Находка — красный тест
   плюс отчёт; прод-код ревьюер не правит.
4. **Приёмка (я).** `awf_verify_pack` (файл GATES), вердикт `prove_red`,
   отчёт ревьюера, минимальность diff, `awf_tree_sha`, затем **повтор
   сценария аудита на принятом коде** (для A-11 — повторный init с активным
   TODO и архивом; для A-12 — коллизии; для A-01 — чужой staged файл). Всё
   сошлось — `awf_approve` с evidence и verified_sha; иначе REVIEW.
5. **Журнал.** `.agentic/context/STABILIZATION-LOG.md`: инвариант, состав и
   размер diff, результат prove-red, находки ревьюера, повтор сценария
   аудита, дефекты после приёмки, причина повторной работы.

Обязательные негативные сценарии по типу изменения:

| Тип изменения | Минимальная проверка |
|---|---|
| TODO, архив, reset | Повтор, коллизия ID, ошибка после первой записи; прежние файлы при отказе побайтно неизменны |
| Запуск и очередь | Два конкурентных публичных вызова с барьером: один владелец, один переход индекса |
| Git и approval | Чужой staged, грязные tracked/untracked, ошибка hook, изменение после verify, гонка reject/approve |
| Subprocess и восстановление | Таймаут, отказ спавна, прерывание до и после сигнала, повтор после рестарта |
| HTTP и формы | Неверное и повторное решение, большое и неполное тело, ошибка применения после приёма, HTML из данных |
| MCP, CLI, пакет | Одинаковая семантика публичных входов; установка обоих wheel и smoke вне дерева |

Критерий пилота: сравнить четыре юнита с прошлыми по числу неожиданных файлов,
повторных правок и пропущенных негативных сценариев. Выигрыша нет —
пересматриваем процесс до расширения.

## 7. Что не беру и почему

- **Смену модели** — решение владельца. Если другая модель когда-нибудь
  появится, она добавит диверсификацию к разделу 3; план на неё не опирается.
- **Восьмишаговый план в лоб.** Первые шаги совпадают с волнами 1–2, но
  SQLite, отдельное дерево и профили ролей — крупные решения без данных о
  необходимости. Они в таблице «решается по данным».
- **Серия новых реальных прогонов ради бейзлайна.** Данные есть: отчёты
  RUN6–RUN10, `RUN-REPORT-20260924-095649.md` (5 юнитов, 324 минуты), отчёты
  `awf metrics` в `~/Desktop/awf-audit/reports`. Пилотный забег сам станет
  замером.
- **«Ещё один общий прогон всего».** Полный suite уже в `scripts/run-all.sh`;
  добавляю адресные сценарии на переходы (таблица выше) и smoke wheel плагина
  в CI.
