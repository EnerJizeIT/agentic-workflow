# Стабилизация awf и контроль качества агентского кода

**Дата:** 2026-09-25. **Статус:** рекомендации по результатам
[послойного аудита](README.md), не утверждённый backlog. Связанный
[план развития](ROADMAP-PROPOSAL.md) задаёт порядок архитектурных изменений.

## Диагноз

В проекте уже есть `scripts/run-all.sh` с контрактами, ратчетами, полным
pytest и Ruff; `awf prove-red`; `verify-pack`; mutation smoke; 119 файлов
тестов. Добавление ещё одного общего прогона само по себе не закроет найденные
дефекты. Пять P1 и большая часть P2 находятся на переходах между файловым
состоянием, процессами, Git index, решением пользователя и UI. Локальный тест
функции может пройти, пока два публичных вызова вместе нарушают инвариант.

Агентский код особенно склонен наращивать параллельные представления одного
состояния, локальные guards и тесты, которые повторяют предположение автора
реализации. Контроль качества должен проверять фактические побочные эффекты и
границы владения, а не только количество тестов, покрытие или зелёный линтер.

## 1. Режим стабилизации

Сначала закрыть P1 из [реестра аудита](README.md): сохранность TODO/архива
(A-11/A-12), один владелец запуска (A-02), сохранность чужого Git index
(A-01), подтверждение checkpoint (A-03). Для каждого исправления нужен
воспроизводящий сценарий на прежнем коде и проверка сохранности старых данных
после отказа. Затем исправлять P2 по связанным группам: переходы забега,
commit gate, формы/HTTP, метрики. Плановое расширение сценариев вести после
стабилизации основного пути.

**Правило выпуска:** открытый P1 на пути `TODO → run → verify → approve →
commit` блокирует релиз. Для P2 требуется явное решение владельца с описанием
обходного поведения и границ риска; зелёный CI не отменяет это решение.

## 2. Контракт для каждого агентского TODO

Перед изменением кода постановка должна содержать:

1. Один наблюдаемый результат и разрешённую область файлов.
2. Инвариант до и после операции; отдельно — состояние при отказе и повторе.
3. Публичные входы CLI/API/MCP, которых касается изменение.
4. Минимальный сценарий, который ошибается на исходном поведении, и команду
   проверки в существующем `verify`/`prove_red` блоке
   [контракта юнита](../../docs/unit-contract.md).
5. Условие остановки: что агент обязан вернуть на пересогласование, если
   требуется менять соседний протокол, контракт или гораздо больше файлов.

Крупную задачу делить по одному инварианту или переходу. Объём около 300
строк нового продуктивного кода в одном diff — сигнал для ручного разбора, а
не автоматический запрет: важнее число изменённых контрактов и побочных
эффектов. Необъяснённые новые файлы, публичные инструменты или ещё один
источник состояния должны останавливать review до пояснения необходимости.

## 3. Цикл выполнения

1. Агент показывает карту затронутых состояний и файлов до правки.
2. Добавляет регрессионный сценарий и подтверждает `prove_red`: тест падает
   по нужной причине на исходном поведении и проходит после исправления.
   Существующий механизм `awf prove-red` уже поддерживает такой цикл.
3. Вносит минимальное изменение, затем запускает адресные проверки и
   существующие `verify-pack`/`run-all` по принятому проектом порядку.
4. Передаёт факты: фактический diff, команды и результаты, непроверенные
   пути, побочные эффекты. `DONE.json` считать указателем на факты, не
   доказательством корректности.
5. Независимый проверяющий со свежим контекстом читает diff и пытается
   сломать инвариант другим порядком вызовов, ошибкой между двумя записями,
   чужими файлами или повтором операции. Он формирует замечания, а не
   редактирует тот же diff параллельно.

Ревьюеру дать права чтения и запуска безопасных проверок; запись и операции
коммита оставить исполнителю/доверенному ядру согласно роли. В OpenCode
разрешения на действия можно назначать по агентам; формат конфигурации
зависит от версии: [V1](https://dev.opencode.ai/docs/permissions/) и
[V2](https://opencode.ai/v2/docs/permissions) используют разные поля.
Ограничения инструментов дополняют проверки в `awf` и не заменяют их.

## 4. Обязательные сценарии по типу изменения

| Изменение | Минимальная проверка |
|---|---|
| TODO, архив, reset | Повтор, коллизия ID, ошибка после первой записи; прежние файлы побайтно неизменны при отказе. |
| Запуск и очередь | Два конкурентных публичных вызова с барьером; один владелец, один переход индекса. |
| Git и approval | Чужие staged изменения, dirty tracked/untracked, ошибка hook, изменение после verify, гонка reject/approve. |
| Subprocess и восстановление | Тайм-аут, отказ спавна, прерывание до/после сигнала, повтор после рестарта. |
| HTTP и формы | Неверное/повторное решение, неполное или большое тело, ошибка применения после приёма, HTML из пользовательских данных. |
| MCP, CLI, пакет | Одинаковая семантика публичных входов; установка обоих wheel и smoke вне исходного дерева. |

Для переходов состояния полезна модельная проверка последовательностей
действий и инвариантов; это соответствует подходу
[stateful testing в Hypothesis](https://hypothesis.readthedocs.io/en/latest/stateful.html).
Её стоит вводить на одном критическом агрегате, например TODO lifecycle,
после обычных конкретных регрессий. Контролируемый shim для настоящего
subprocess контура уже намечен в [`BACKLOG.md`](../../BACKLOG.md).

## 5. Критерий качества diff

Проверяющий отвечает на шесть вопросов:

1. Изменился ли один заявленный контракт или агент незаметно расширил API?
2. Есть ли второй парсер, второй статус, второй guard либо дублирование
   прежнего кода вместо использования владельца операции?
3. Что произойдёт после ошибки ровно между чтением и записью, между
   `approve` и коммитом, между спавном и фиксацией состояния?
4. Затронуты ли пользовательские файлы, Git index, другие TODO или архив?
5. Проверяет ли тест публичный исход и побочные эффекты, или лишь вызов mock?
6. Можно ли удалить часть нового кода без потери заявленного поведения?

Существующий ратчет фиксирует рост числа файлов более 400 строк, но его
baseline в истории уже повышался. Для продуктивных модулей каждый новый рост
должен сопровождаться отдельным решением о владельце ответственности и
возможности разрезать модуль. Счётчик упоминаний `TODO` в тестах и текстах
не следует принимать за показатель качества архитектуры.

## 6. Ворота CI и качество самих тестов

Сохранить один `run-all.sh` как общий обязательный прогон. Добавить адресные
регрессии из таблицы выше на критических переходах и smoke установленного
wheel плагина. Mutation testing применять выборочно к `pipeline_engine`,
`awf/api`, состоянию и commit gate: выжившая мутация указывает на слабый тест,
но не требует полного проекта под mutmut в каждом PR. Новый автоматический
гейт сначала должен поймать демонстрационное нарушение, как уже требует
проектный `AGENTS.md`.

Отдельно проверять сами тесты: не переносят ли они ошибочный контракт в
ожидание, не скрывают ли гонку чрезмерным mock и сохраняют ли прежние байты
после отказа. Приоритет измерения — доля критических переходов с негативным
сценарием, а не число тестовых функций.

## 7. Обратная связь по агентской работе

Для каждого принятого юнита сохранять: заявленный инвариант, размер и состав
diff, результат `prove_red`, замечания независимого review, дефекты после
принятия и причину повторной работы. Раз в несколько юнитов искать
повторяющийся класс ошибок и менять один конкретный контракт, инструмент или
роль. Метрики «строк написано» и «тестов добавлено» не считать успехом.

**Первый проверяемый цикл:** взять A-11, A-12 и A-01; оформить три отдельных
TODO по этому шаблону, пропустить через независимое review и сравнить число
неожиданных файлов, повторных правок и пропущенных негативных сценариев с
предыдущими юнитами. Это проверит сам процесс качества до его расширения на
весь проект.
