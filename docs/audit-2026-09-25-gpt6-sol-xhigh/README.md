# Послойный аудит agentic-workflow

**Дата:** 2026-09-25. **Ветка:** `post-audit`. **Метка папки:** `gpt6-sol-xhigh`. **Формат:** тринадцать последовательных ревью по ролям, каждое сохранено отдельно; этот файл объединяет результаты.

## Объём и метод

В репозитории 110 Python-файлов продуктивного кода (31 152 строки) и 119 Python-файлов тестов (42 230 строк). Просмотрены основные публичные входы CLI/API/MCP, жизненный цикл TODO и забега, исполнение стадий, Git/approve/verify, локальные HTTP обработчики, формы, метрики, вспомогательные проверки, контракты, тестовые сценарии, CI и упаковка. Дополнительно выполнены AST-поиск неиспользуемых определений, разбор крупных функций, контролируемые сценарии восстановления и smoke собранных wheel. ## Итоговая оценка

Найден **21 дефект: 5 P1, 14 P2 и 2 P3**, а также **3 кандидата на неиспользуемый код и 7 рекомендаций по рефакторингу**. Самый высокий риск связан с потерей состояния и истории TODO, одновременной работой двух пайплайнов и включением посторонних изменений в коммит. Отдельно checkpoint принимает решение через локальный POST без привязки к конкретной форме. Уровень означает возможный ущерб по коду, а не наблюдённую частоту. Гонки запуска подтверждены в контролируемых сценариях с подменой спавна; их частота в эксплуатации не измерялась.

У проекта есть сильная основа: явные контракты, большой набор unit/integration/e2e/negative сценариев, блокировки отдельных операций, атомарная запись ряда файлов, тайм-ауты subprocess. Статическая команда `ruff check awf agent_workflow_ui/src --output-format concise` прошла без замечаний; 122 адресных теста прошли. Оба wheel установились и прошли smoke на Python 3.10, 3.11 и 3.12. Эти меры пока не закрывают сквозные переходы между процессами, файлами, Git index и UI.

## Мёртвый код и рефакторинг

[Отдельный разбор неиспользуемого кода](10-dead-code.md) выделил `read_include_list`, `working_tree_clean` и `load_reference_costs`: внутри репозитория вызовов нет. Это **кандидаты**, поскольку внешние потребители публичных модулей и динамические обращения статически не исключены. `read_include_list` особенно показателен: `run_next` вручную повторяет его разбор файла. Частных top-level функций без внутренних обращений AST-проход не обнаружил.

[Отдельный план рефакторинга](11-refactoring.md) содержит семь конкретных шагов: единое владение запуском, общий слой хранения TODO, проверяемый план коммита, разделение HTTP submit и применения, разрезание сбора метрик, единый реестр MCP tools и удаление второго парсера `.include`. Первые три непосредственно закрывают наиболее опасные нарушения инвариантов; остальные уменьшают число мест, где формат или статус может разойтись.

## Динамические проверки восстановления и пакетов

[Слой восстановления](12-recovery-reliability.md) подтвердил на временных проектах потерю активного TODO/архива при повторном `init` (**A-11**), перезапись при `restore` (**A-12**), конкурирующие `run_start` (**A-13**) и окно двойного `start_pipeline` (**A-02**, со спавном-заглушкой). Прерванное архивирование в одном проверенном месте удалось завершить повторным вызовом. Новый сценарий **A-21** показал, что отказ запуска сохраняет `.ready`, хотя API отвечает `refused`.

[Слой установленных пакетов](13-installed-packages.md) проверил оба wheel из `site-packages` на Python 3.10.21, 3.11.16 и 3.12.3: CLI, регистрацию 47 MCP tools, packaged assets, рендер форм и запуск entry point. Ошибок упаковки в этой матрице не найдено; **A-18** остаётся задачей для CI, где wheel плагина пока не smoke-устанавливается.

## Сквозные причины

1. **Право единственной записи не охватывает всю операцию.** Локальные lock защищают отдельные файлы, но `check → start`, `check → run state`, `approve → signal` и `verify → commit` остаются несколькими независимыми шагами (**A-02, A-04, A-13, A-15**).
2. **Состояния интерфейса и действия расходятся.** `submitted` означает получение формы, а не успешное применение; `False` от commit gate не всегда останавливает стадию (**A-05, A-14**).
3. **Идентичность и границы данных проверяются частично.** ID проверяется в текущем inbox, но не во всём жизненном цикле; отпечаток не охватывает байты untracked файла; пути тестов не удерживаются в корнях (**A-09, A-12, A-19**).
4. **Отчётность зависит от неявных соглашений формата.** Четыре цифры TODO и слово `verify` в теме коммита не совпадают с публичными контрактами (**A-10, A-17**).

## Очередность реализации всего аудита

Порядок основан на риске потери пользовательских данных, неожиданного коммита
и зависимостях между исправлениями. Номер ниже означает этап, а не один
большой PR: внутри этапа исправления можно принимать отдельно. Для каждого
дефекта сначала закрепить сценарий, который показывает старое поведение,
затем проверить исход после исправления и сохранность прежних данных при
отказе. Существующие `prove_red`, `verify-pack` и `run-all.sh` описаны в
[плане контроля качества](QUALITY-STABILIZATION.md).

0. **Зафиксировать исходное поведение.** Для каждого из пяти P1 получить
   отдельное воспроизведение на изолированном проекте до исправления.
   **Готово:** сценарии ловят прежнее поведение и не затрагивают рабочее
   состояние пользователя.

1. **Остановить потерю данных и опасные действия — все P1, в таком порядке:**
   **A-11** — обычный повторный `init` сохраняет runtime и архив;
   **A-12** — `dispatch`, `restore` и `archive` отказывают при занятом ID,
   сохраняя обе версии файлов; **A-01** — коммит использует изолированный
   index и учитывает изменения, существовавшие до baseline, не трогая
   пользовательский index; **A-02** — атомарное право единственного запуска
   охватывает foreground и background; **A-03** — checkpoint принимает
   одноразовое решение только от соответствующей формы. Каждое из пяти
   исправлений — отдельный обозримый шаг. **Готово:** повтор, коллизия,
   параллельный запуск, чужой staged файл и посторонний POST не приводят к
   потере данных, второму владельцу или неожиданному решению/коммиту.

2. **Закрыть независимые границы и усилить CI — A-19, A-07, A-16, A-06,
   A-18.** Удержать
   путь `prove-red` внутри временного worktree (**A-19**), ограничить размер
   и время чтения HTTP тела (**A-07**), экранировать данные моделей и скиллов
   в HTML (**A-16**), валидировать форму и типы ручного YAML до создания
   стадий (**A-06**). Добавить в CI smoke *установленного* wheel плагина
   наряду с core wheel (**A-18**) до переработки ядра и MCP. Эти изменения
   не должны ждать реорганизации движка.
   **Готово:** неверный ввод даёт управляемый отказ без записи вне выбранной
   области, зависания обработчика или исполнения HTML из данных; оба wheel
   проходят установленный smoke.

3. **Свести владение TODO и забегом в один переход — A-13, A-21; R-01/R-02,
   D-01/R-07.** После защиты старта из A-02 перенести проверку активности и
   запись очереди под одно право владения, с поколением забега и условным
   обновлением индекса (**A-13**). При отказе запуска восстанавливать прежний
   `.ready` (**A-21**). Сосредоточить `dispatch/archive/restore` в одном слое
   хранения; при изменении `run_next` убрать второй парсер `.include`, выбрав
   одну реализацию `read_include_list` (**D-01/R-07**). **Готово:** два
   конкурентных вызова запускают один элемент ровно один раз, а отказ
   оставляет очередь и сигнал в исходном состоянии.

4. **Сделать подтверждение и коммит одной проверяемой цепочкой — A-04,
   A-09, A-14, A-15; R-03, D-02.** Решение `approve/reject` публиковать
   вместе с проверенным поколением; конфликт не оставляет разрешающий сигнал
   (**A-04**). Использовать бинарно безопасный отпечаток дерева, включая
   содержимое untracked файлов (**A-09**). Отказ commit gate возвращать
   явным результатом и останавливать execute стадию (**A-14**); сверять
   проверенное содержимое прямо на пути к коммиту (**A-15**). Оформить это
   как `CommitPlan` поверх изоляции A-01. После проверки внешнего контракта
   решить судьбу неиспользуемой обёртки `working_tree_clean` (**D-02**).
   **Готово:** rejected verdict или изменение после verify не может дать
   коммит; отказ gate не переводит стадию дальше; чужой index сохраняется.

5. **Выравнять формы и MCP — A-05, A-20, A-08; R-04/R-06.** Разделить
   `received`, `applied` и `failed`, чтобы форма сообщала итог применения,
   а не только факт POST (**A-05/R-04**). Блокирующий baseline и другие
   синхронные API вызовы выполнять вне event loop (**A-20**). Вести список
   MCP tools из одного проверяемого реестра и синхронизировать с ним
   документацию (**A-08/R-06**). **Готово:** ошибка применения видна через
   MCP, соседние запросы обслуживаются во время долгой операции, число и
   список tools совпадают с регистрацией.

6. **Исправить отчётность после стабилизации источников событий — A-10,
   A-17; R-05, D-03.** Ввести общий парсер TODO ID и собственного формата
   commit subject, включая пятизначные ID (**A-10**); учитывать допустимые
   коммиты вне стадии `verify` (**A-17**). Разделить сбор фактов, расчёт и
   рендер метрик (**R-05**). После проверки публичной совместимости решить,
   нужна ли неиспользуемая `load_reference_costs` (**D-03**). **Готово:**
   отчёт не теряет пятизначные TODO и коммиты других стадий; расчёт можно
   проверять на подготовленных фактах без Git и SQLite.

7. **Выпустить после сквозной проверки.** Пройти полный `run-all.sh`,
   адресные конкурентные и отказные сценарии, установленный smoke обоих
   wheel, затем несколько реальных забегов с настоящими worker subprocess.
   Сверить поведение CLI и MCP, миграцию старого состояния и восстановление
   после прерывания. **Готово:** для всех 21 дефектов есть исправление и
   регрессия либо документированное решение владельца; три кандидата на
   неиспользуемый код проверены на совместимость, а семь рефакторинговых
   рекомендаций реализованы или явно отложены с причиной. Результат одного
   прогона не заменяет наблюдение последующих выпусков.

Порядок первых изменений на практике: **A-11 → A-12 → A-01 → A-02 → A-03**.
Остальные этапы опираются на эти границы. Более широкий вариант
архитектурного развития сохранён в [предложении по roadmap](ROADMAP-PROPOSAL.md).

## Границы достоверности

Статические выводы дополнены адресными воспроизведениями, но реальные worker subprocess, `SIGKILL`, потеря питания, браузерная атака и запись за пределы worktree не моделировались. Поиск неиспользуемого кода не доказывает, что у публичных функций нет внешних вызывающих. Полный test suite не запускался: его успешное прохождение и отсутствие других дефектов не утверждаются. Исходный код проекта не менялся; результат самого аудита — тринадцать послойных файлов и данный сводный отчёт. Последующие предложения о развитии и качестве сохранены отдельно и не являются подтверждением исправления находок.
