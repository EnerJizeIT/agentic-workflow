# Слой 4 — Git, подтверждение и проверка результата

**Роль:** инженер целостности коммита. Просмотрены baseline, Git index, approve/reject, автоматический commit gate, дерево изменений и признаки работы стадии.

## A-01 · P1 · Коммит юнита включает чужое содержимое Git index

[_commit_specific_files](../../awf/commit_gate.py#L149) выполняет `git add -- <files>`, затем обычный `git commit -m`. Такой commit включает **весь** текущий index, в том числе файлы, staged до запуска awf и отсутствующие в `files`. При отказе коммита выполняется `git reset`, который снимает и посторонние staged изменения ([строка 177](../../awf/commit_gate.py#L177)). `git diff --name-only <baseline SHA>` отбирает имена, но SHA не отделяет tracked правки, существовавшие до baseline.

**Рекомендация:** отдельный временный Git index для единицы работы либо отказ при чужом staged состоянии с сохранением исходного index при любом исходе. Для tracked файлов сохранять исходный снимок содержимого, если требуется именно граница «изменения worker после baseline».

**Проверка после исправления:** заранее staged посторонний файл и ранее изменённый tracked файл не входят в коммит юнита; при провале hook исходное staged состояние остаётся прежним.

## A-04 · P2 · Конфликт reject/approve оставляет разрешающий сигнал

[`approve_commit`](../../awf/api/pipeline.py#L378) создаёт `APPROVE-<id>.ready` до проверки свежего состояния забега под lock. Если reject уже записан, mutator сохраняет verdict `rejected` и сообщает о конфликте ([строка 392](../../awf/api/pipeline.py#L392)), но файл разрешения остаётся. Интерактивное ожидание проверяет ACK/APPROVE раньше REVIEW ([supervisor.py](../../awf/supervisor.py#L607)); автоматический [commit gate](../../awf/commit_gate.py#L224) ждёт файл APPROVE/ACK без сверки verdict. При подходящем порядке событий коммит может пройти при rejected verdict.

**Рекомендация:** публиковать сигнал только после успешной атомарной записи решения; при конфликте возвращать отказ без файла. Перед коммитом проверять актуальный verdict и идентификатор цикла.

**Проверка после исправления:** reject → approve и параллельные вызовы не создают commit при rejected verdict.

## A-09 · P2 · Отпечаток работы стадии не хеширует содержимое untracked файлов

[`work_fingerprint`](../../awf/verify.py#L69) складывает текст `git diff` и имена untracked файлов, но не их байты ([строка 115](../../awf/verify.py#L115)). [`execute_agent_stage`](../../awf/pipeline_engine.py#L919) сравнивает этот хеш до и после стадии. Если файл уже создан предыдущей стадией и следующая меняет только его содержимое, отпечаток остаётся прежним: стадия ошибочно выглядит бездействующей и может попасть в повтор/salvage. Для бинарного tracked файла текстовый `git diff` тоже недостаточен. В коде уже существует более полный [`tree_fingerprint`](../../awf/git_utils.py#L98).

**Рекомендация:** единый бинарно безопасный отпечаток дерева с исключением только файлов, заведомо бывших до baseline. **Проверка:** изменение байтов существующего untracked или бинарного tracked файла меняет stage fingerprint.

## A-15 · P2 · `verified_sha` не защищает интервал до коммита

[`approve_commit`](../../awf/api/pipeline.py#L338) сравнивает переданный `verified_sha` с текущим деревом и записывает `VERIFIED-<id>.sha`. Затем публикуется сигнал APPROVE. Но [`maybe_commit`](../../awf/commit_gate.py#L199) читает только сигналы и baseline; `VERIFIED` файл нигде на commit path не сверяется (его другое использование — отчёт забега). Изменение дерева после `approve` и до `git add/commit` может попасть в коммит без повторной независимой проверки. Параметр опционален, поэтому рекомендация относится к сценарию, где пользователь его передал.

**Рекомендация:** перед staging и сразу после staging проверять тот же отпечаток либо фиксировать проверенное содержимое в отдельном index, который и коммитится. При расхождении остановить commit и потребовать новой проверки.

**Проверка после исправления:** изменение любого tracked/untracked файла после `approve(verified_sha=...)` не попадает в коммит.
