# Предложение по развитию awf после аудита

**Дата:** 2026-09-25. **Автор предложения:** GPT-6 Sol XHigh.
**Статус:** личная рекомендация по результатам аудита, не утверждённый план
владельца проекта. Утверждённые и ожидающие задачи ведутся в
[`BACKLOG.md`](../../BACKLOG.md).

## Цель

Один TODO должен проходить от постановки до проверенного коммита так, чтобы
после сбоя можно было установить фактическое состояние и безопасно продолжить.
Приоритет развития — сохранность задачи и архива, единственный владелец
исполнения, однозначное решение пользователя и коммит ровно проверенного
содержимого. Основание: [сводный аудит](README.md) и
[разбор рефакторинга](11-refactoring.md).

## Шаг 1. Зафиксировать инварианты и базовую оценку

Описать публичные состояния TODO, забега, стадии, решения и коммита вместе с
допустимыми переходами. Для каждого инварианта записать сценарий сбоя,
ожидаемый ответ API и действие восстановления. Собрать базовую серию реальных
прогонов: время до принятого результата, число вмешательств, повторов и
причины отказов. Это даст критерии приёмки следующих шагов.

**Готово, когда:** опубликован один контракт переходов, а каждую находку P1
можно связать с нарушенным инвариантом и проверкой после исправления.

## Шаг 2. Выпустить исправления сохранности и границ доступа

Сделать повторный `init` безопасным для существующих TODO и архива; проверять
коллизии ID во всех каталогах до `dispatch`, `restore` и `archive`
(**A-11/A-12**). Закрыть одновременный старт одной проектной блокировкой
(**A-02**). До переработки Git отказывать в коммите при чужом staged
состоянии, сохраняя исходный index (**A-01**). Привязать решение checkpoint
к конкретной одноразовой форме (**A-03**).

**Готово, когда:** повторный `init`, коллизия ID, параллельный старт,
посторонние staged файлы и поддельный запрос не приводят к потере данных,
второму исполнителю или неожиданному коммиту. Предыдущее содержимое
сравнивается побайтно после отказа.

## Шаг 3. Создать единый источник управляющего состояния

Использовать SQLite для состояния забега, очереди, стадии, решений и журнала
событий; тексты TODO, handoff и логи оставить файлами. Ввести поколение забега,
уникальную резервацию TODO и ключ повторного вызова операции. Переходы
`inactive → active`, `reserved → running` и обновление индекса очереди
выполнять транзакционно с проверкой ожидаемого предыдущего состояния
(**A-02/A-13/A-21**). Файловые побочные эффекты оформлять как
восстанавливаемые шаги с записью намерения и итога: транзакция базы сама по
себе не делает запись файлов и Git атомарной.

**Порядок внедрения:** слой хранения за существующим API, миграция текущего
состояния с резервной копией и проверкой, затем перевод публичных операций по
одной. На каждом этапе один источник считается авторитетным.

**Готово, когда:** два конкурентных `run_start`/`run_next` дают ровно одного
владельца и один переход очереди; после прерывания состояние однозначно
восстанавливается.

## Шаг 4. Связать проверку, решение и коммит

Ввести `CommitPlan`: TODO ID, поколение забега, список файлов, отпечатки
содержимого, ожидаемое решение и исходный Git tree. Ближайший шаг — временный
изолированный Git index; целевой режим для задач с изменением кода — отдельное
рабочее дерево на забег. Перед коммитом сверять проверенное содержимое с
планом и текущим решением. `reject` и отказ commit gate должны останавливать
переход стадии (**A-01/A-04/A-09/A-14/A-15**).

**Готово, когда:** чужой index неизменен и при успехе, и при ошибке hook;
изменение файла после approve останавливает коммит; rejected verdict не
может породить коммит; в коммит входят только перечисленные проверенные файлы.

## Шаг 5. Упростить движок исполнения и восстановление

Заменить неоднозначные `bool` и комбинации сигналов типизированными
результатами переходов (`started`, `refused`, `failed`, `completed`) с причиной.
Разделить длинные обработчики стадий по переходам и побочным эффектам.
После рестарта сверять журнал, процесс и артефакты; повтор операции должен
либо безопасно завершать начатое, либо возвращать точную причину остановки.
Файлы сигналов оставить транспортом на период совместимости, а не источником
права на запуск или коммит.

**Готово, когда:** прерывание в каждой ключевой точке оставляет наблюдаемое
состояние; повторный вызов не запускает второго worker и не перескакивает
стадию.

## Шаг 6. Выравнять CLI, MCP и формы

Сделать `awf.api` единой публичной границей для CLI и MCP; заменить импорты
частных модулей плагином. Для формы разделить `received`, `applied` и
`failed`; добавить лимиты и тайм-ауты HTTP чтения, экранирование HTML и
одноразовое подтверждение (**A-03/A-05/A-07/A-16**). Синхронные операции MCP
вызывать вне event loop (**A-20**). Вести регистрации tools и документацию
из одного реестра; показывать агенту только нужный для роли профиль.

**Готово, когда:** CLI и MCP возвращают одинаковый итог одного перехода,
форма не объявляет успешное применение до записи результата, документация
совпадает с реестром tools.

## Шаг 7. Проверять границы системы в CI и на реальных прогонах

Добавить сценарии конкурентного запуска, сбоев между записями, повторных
вызовов, отказа subprocess, изменения дерева после проверки и сохранности
пользовательского index. Использовать управляемый shim OpenCode для
интеграционных сценариев, затем реальные прогоны на нескольких репозиториях и
как минимум двух моделях. В CI устанавливать и проверять оба собранных wheel
на поддерживаемых версиях Python (**A-18**). Поддерживать матрицу версий
OpenCode/MCP: [документация OpenCode V2](https://opencode.ai/v2/docs/mcp-servers)
уже описывает отдельную структуру `mcp.servers` и выбор версии протокола.

**Готово, когда:** критические инварианты подтверждены тестами с реальными
файловыми и Git операциями, а полные пользовательские прогоны дают
воспроизводимый отчёт об успехах, отказах и стоимости.

## Шаг 8. Расширять сценарии на основе данных использования

После стабилизации основного пути выбрать одно расширение: профиль задач по
документации/аналитике, другой агентный хост или лестницу моделей. Решение
принимать по наблюдаемым отказам и запросам пользователей. Для каждого
профиля явно задать политику проверки, набор инструментов и критерий
готовности. Сбор метрик выполнять по запросу владельца, как уже указано в
[`BACKLOG.md`](../../BACKLOG.md).

**Готово, когда:** новый сценарий демонстрирует измеримую пользу в реальных
прогонах и проходит те же инварианты сохранности и восстановления.

## Первые три изменения

1. Безопасный повторный `init` и защита от коллизий TODO ID.
2. Единственное владение запуском с проверкой перехода внутри блокировки.
3. Защита пользовательского Git index и явный результат commit gate.

Эта последовательность снижает самые тяжёлые риски до начала крупной
переработки состояния и интерфейсов.
