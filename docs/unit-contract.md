# Контракт юнита (U3)

Необязательный машиночитаемый контракт по TODO: план-stage объявляет, что и
как проверять, исполнитель отчитывается машиночитаемыми фактами вместо прозы.
Всё необязательно — TODO без блока и DONE без json работают ровно как раньше.

## Блок в TODO (front-matter)

В самом верху TODO-файла, между двумя строками `---`. Строки-комментарии
`<!-- ... -->` (например role hint, который добавляет dispatch) до блока
пропускаются. Заголовок `# TODO — <название>` тоже может стоять выше блока:
контракт, записанный сразу под заголовком, читается так же (пропускается
ровно один заголовок первого уровня; горизонтальная черта дальше в теле
блоком не считается).

```yaml
---
verify: ["python3 -m pytest tests/unit/test_x.py -q"]
gates: ["contracts", "ratchet"]
prove_red: ["tests/unit/test_x.py::test_y"]
---
# TODO-0001 — задача

тело…
```

Ключи (все необязательны, но объявленный ключ обязан быть заполнен):

- `pipeline` — имя пайплайна для запуска в забеге (строка, не список).
  Когда `awf_run_next` запускает TODO без пайплайна на уровне очереди
  забега, он берёт имя отсюда (RUN3 #2). Имя — как у пайплайнов: буквы,
  цифры, `_`, `.`, `-`; пустое имя не принимается (пусто = пайплайн из
  config, ключ просто не пишут). `awf_dispatch_todo(..., pipeline=...)`
  пишет ключ в блок автоматически (блок создаёт, если его нет).
- `replan_for` — маркер replan-ответа (BD-30, TODO-0213): id юнита,
  которого заменяет этот TODO (строка, `TODO-NNNN`). Replan-вейт
  (интерактивный `wait_for_supervisor_signal` И auto-субпроцесс —
  watcher с фильтром и fallback-детектор; kind="replan") подхватывает
  свежий TODO как ответ супервизора только при маркере, называющем
  эскалированный юнит; обычный mid-run диспатч без маркера живой
  пайплайн не трогает. Без маркированного ответа пайплайн
  останавливается на заблокированном юните (BLOCKED остаётся;
  dispatch с маркером + `awf continue` продолжает).
  `awf_dispatch_todo(..., replan_for=...)` пишет
  ключ в блок (блок создаёт, если его нет); ручная строка в блоке
  работает так же. Референт обязан существовать и быть живым
  (inbox-юнит без DONE-закрытия; архивный или done-юнит — отказ до
  побочных эффектов).
- `verify` — список непустых команд проверки.
  Команды исполняются как argv (без shell), поэтому shell-операторы вне
  кавычек — отказ валидации контракта (диспатч отбивает юнит): `&&`, `||`,
  `;`, `|`, `>`, `<`, фоновый `&`, подстановка команд `$(` и бэктики
  (REVIEW витки 2–3 TODO-0232). Нужна склейка или подстановка — пиши
  скрипт, отдельные команды или цитируй оператор аргументом `sh -c "..."`.
  Окружение задаётся через `env VAR=val команда …` (префикс `VAR=val`
  без `env` — это `argv[0]`, команда не найдётся). Globbing (`a*`) —
  литерал: argv-запуск звёздочку не раскрывает, передавай готовый путь.
  Те же правила действуют для команд из конфига
  (`verification.test_cmd` / `baseline_cmd` etc.): это тот же argv-класс,
  shell-оператор там — отказ, а не молчаливый литерал (REVIEW виток 6
  TODO-0232). Внутренний перевод строки (`\n`, `\r`, `\r\n`) —
  тоже отказ («multi-line verify», REVIEW виток 5 TODO-0232); хвостовой
  `\n` блочного скаляра (`- |`) нормализуется — команда остаётся одной.
- `flake` — переключатель флейк-пробы (M1): `on` (по умолчанию) или `off`.
  Пробуются только тест-подобные команды (`pytest` / `py.test` /
  `python -m pytest`, в том числе через venv-путь) — они выполняются
  дважды. `off` выключает пробу: каждая команда `verify:` выполняется
  один раз. Разбор сводки pytest (ниже) от `flake` не зависит.
- `xfail_allow` / `skip_allow` — сколько `xfailed` / `skipped` юнит
  разрешает в тест-подобной команде `verify:` (неотрицательное целое,
  по умолчанию 0). Допуск действует на каждую команду отдельно, не
  суммарно. При rc 0 число выше допуска — FAIL с командой и числами;
  в пределах — pass со строкой `allowed N xfailed, M skipped`. rc≠0
  остаётся FAIL при любом допуске. `xpassed` не судится: pass со строкой
  о числе (устаревший xfail). Отрицательное число или строка —
  ошибка контракта.
- `gates` — список коротких имён проверок: канонический набор
  `KNOWN_GATES` из `awf/unit_contract.py`
  (`contracts`, `ratchet`, `instructions`, `tests`, `lint`, `mutations`).
  Это НЕ «имена проверок из run-all.sh»: `scripts/run-all.sh` гоняет
  `contracts`/`ratchet`/`instructions` под этими короткими именами, а
  pytest- и ruff-команды — строками из `scripts/project-commands.txt`
  (это и есть `tests`/`lint`); `mutations` в run-all не входит:
  базовый набор (4 мутации, `scripts/mutations.txt`) гоняется в CI test-job
  отдельным шагом `scripts/mutation-smoke.sh`, а `--report`-прогон
  (`scripts/mutations-neg5.txt`) остаётся ручным шагом. В verify-pack секция
  `gates` исполняет только первые три; `tests`/`lint` покрывают команды
  из `verify:`, а `mutations` — декларация для QA и для CI-базового набора.
- `prove_red` — список тест-идов, которые обязаны быть красными до фикса.
  `awf prove-red --todo <id>` проверяет это машинно (baseline в worktree:
  красный от ассерта + зелёный на текущем дереве; вердикты `red-ok` /
  `not-red` / `broken-runner` / `green-after`) — в отличие от `verify`,
  который просто прогоняет команды проверки на текущем дереве.
- `prove_red_pin` — список тест-идов-щитов: они фиксируют УЖЕ работающее
  поведение, поэтому на baseline обязаны быть ЗЕЛЁНЫМИ. Это противополож-
  ность `prove_red`: там тест обязан падать до фикса, а «зубы» пина (что щит
  реально поймаёт регресс) доказываются мутацией, вне инструмента.
  `prove_red` и `prove_red_pin` взаимоисключимы — оба сразу в одном TODO
  это ошибка контракта. `awf verify-pack` прогоняет пин на baseline: все
   зелёные → вердикт `pin-ok` (секция pass, не fail, с пометкой «регресс-щит;
   зубы вне автоматики»); КРАСНЫЙ на baseline → `fail` (это не пин, а находка
   — тест падает на старом коде); ошибка коллекции → `broken-runner`.
- `prove_red_kind` — объявленный тип prove-red-проверки (строка). Два типа:
  - `coverage` — юнит-покрытие/валидация: его тесты проверяют
    поведение, внедрённое РАНЕЕ (в других юнитах), поэтому на baseline этого
    юнита они зелёные по построению, и prove-red честно вернёт `not-red`.
    С объявленным kind вердикт `not-red` — PASS секции `prove_red` в
    verify-pack с пометкой «coverage unit — not-red is expected (declared)»
    и записью `prove_red_note` в отчёт, а не провал.
  - `new-api` — юнит нового модуля/символа: тест падает на baseline только
    потому, что символа ещё нет (prove-red помечает такую причину типизированным
    фактом `new_code_acceptable`, а не текстом предупреждения). С объявленным
    kind этот вердикт — `new-api-ok`: PASS с предупреждающей секцией, exit-код
    verify-pack остаётся 0. Настоящая поломка раннера (ошибка коллекции вне
    проекта, 0 тестов, таймаут) остаётся fail.

  Остальные вердикты (`red-ok` — pass как раньше, `green-after`/реальный
  `broken-runner` — fail) и все прочие секции объявлением не затрагиваются.
  Kind требует `prove_red` (тип модифицирует именно эту проверку) и
  `prove_red_note`; взаимоисключим с `prove_red_pin` (оба ждут зелёный на
  baseline, но по разным причинам — объявленное покрытие против
  регресс-щита).
- `prove_red_note` — обоснование для `prove_red_kind` (непустая строка),
  записывается в GATES-отчёт. Ключи — пара: объявление одного без другого
  — ошибка контракта.

Пример coverage-юнита:

```yaml
---
prove_red: ["tests/test_presets.py"]
prove_red_kind: coverage
prove_red_note: "поведение пресетов внедрено в U2; этот юнит только добавляет покрытие"
---
```

Без объявления `not-red` не смягчается (останется провалом), но если дифф
юнита — только тестовые пути (никаких правок исходников), verify-pack
добавит в GATES-отчёт строку-подсказку объявить
`prove_red_kind: coverage` + note. Это подсказка, не автоподмена
вердикта.

Валидация в `awf/api/dispatch.py::dispatch_todo` (один путь для MCP и CLI):

- блока нет — не ошибка;
- битый YAML, ключ не-списком, пустой список, пустая строка в списке,
  неизвестное имя gate — `AwfApiError` с текстом, что именно не так и как
  правильно;
- неизвестный ключ в блоке (опечатка) — не ошибка, но предупреждение в
  `pre_check_warnings` ответа dispatch.

- `checklist_classes` — список классов проверок завершения (строки,
  непустой список). Классы объявлены явно: неизвестный класс — отказ
  диспатча, дубли id между базой, классами, волной и приёмкой — тоже
  отказ. Подсказки по разделу «Границы» печатаются строкой
  `checklist_suggested:` и сами не мержатся (TODO-0244); объявленный
  класс в подсказки не попадает.
- `wave` — имя волны (слаг: буквы, цифры, `_`, `.`, `-`). Волна лежит в
  `<project>/.agentic/checklists/waves/<name>.yaml` и добавляет свои
  пункты в чек-лист юнита. Пропущенный файл волны — отказ диспатча,
  ключ просто не пишут для одиночного юнита (TODO-0244).

## Чек-лист завершения (DoD)

При диспатче в TODO дописывается блок `## Чек-лист завершения`: базовый
набор + объявленные классы + пункты волны + приёмочные пункты юнита
(секция `## Приёмка`, по одному на строку). Блок фиксируется в файле:
правка волны посреди юнита живой юнит не меняет. Строка блока:

```
- [ ] <id>: <text> — probe(<type> <args>) expect <...>
- [ ] <id>: <text> — probe(command_rc timeout=<n> <argv>) expect rc=<n>
- [ ] unit-01: <критерий приёмки> — manual
```

Однострочный текст пишется как есть; многострочный, с краевыми пробелами
или неоднозначный (кавычка в начале, ` — probe(` внутри) — JSON-строкой,
чтобы перевод строки, кавычки и юникод пережили заморозку и разбирались
ровно тем же значением. Аргументы пробы пишутся одним JSON-массивом
(`["git", "status"]`) и читаются обратно тем же разбором: табуляция,
перевод строки и кавычки в шаблоне не превращаются в текст эскейпа.
Старые блоки с shell-цитированием читаются как есть.

`manual` — пункт без пробы, его проверяет принимающий; гейт такие пункты
не считает проваленными.

Разбор блока не теряет пункты. Читается любой маркер списка (`- [ ]`,
`* [ ]`, `+ [ ]`, голый `[ ]`) и отступ: пункт — это пункт, а не проза.
Строка, которая похожа на чекбокс, но не разбирается, — ошибка, а не
пропуск. `expect` у `grep_*`/`file_*` — строго `present` или `absent`:
опечатка не инвертирует проверку молча. Заголовок блока без пунктов —
провал (`(empty block)`), а не пройденный чек-лист; «блока нет» и «блок
пуст» — разные факты. Путь пробы (`file`, `path`) проверяется, как
позиционный аргумент `command_rc`: при загрузке данных и при разборе
блока он не может выйти за корень проекта, а на прогоне такой пункт
падает сам, не обрывая остальные.

Таймаут пробы живёт в блоке: у `command_rc` необязательный
`timeout=<n>` стоит сразу после типа пробы и применяется при прогоне.
Значение по умолчанию — 120 секунд (потолок схемы), поэтому в строке
его не пишут. Блок — единственный источник, который исполняет гейт,
так что объявленный в YAML таймаут переживает заморозку, а не
подменяется потолком.

Гейт исполняет пробы и пишет `context/CHECKLIST-<todo>.json`, привязанный
к отпечатку дерева. Отпечаток дерева не видит `.agentic/` (каталог в
`.gitignore`), а базовые пробы читают именно его, поэтому ключ кэша
включает ещё и цели проб: содержимое для читающих проб и факт наличия для
`file_*`. Тот же ключ и тот же блок — переиспользование, изменился ключ —
пересчёт. Заявления из DONE.json (`checklist` /
`checklist_checked`) — не истина: расхождение с прогоном даёт warning.

`awf checklist show <todo>` печатает блок, `check` — вердикт и пропуски
(rc 0/1), `hash` — sha256 ровно блока, `apply` — пересобирает блок у уже
задиспатченного НЕ начатого юнита (та же композиция и та же проверка
читаемости, что при диспатче; бэкап, идемпотентно; начатый или
архивный — отказ). Подробности и правила обновления —
`docs/design/dod-gate.md`.

## Первоисточник (source_ref)

`dispatch_todo(..., source_ref="<файл>#<секция>")` (CLI:
`awf dispatch --source-ref`) вставляет в TODO раздел первоисточника сразу
после заголовка `# TODO-NNNN` (контрактный блок остаётся первым, заголовок —
первым заголовком: по нему работают защиты номера):

```markdown
# TODO-0001 — юнит

## Первоисточник (R2.5)

- [ ] владелец один
- [ ] второй пункт
```

Секция ищется по точному тексту заголовка (без fallback по первому слову);
два заголовка с одинаковым текстом — явный отказ со списком строк. Тело
идёт до следующего заголовка того же или более высокого уровня; пункты
списка (bullets/numbered) становятся чек-листом, продолжения пунктов,
проза и код-фенсы сохраняются как есть (пример внутри фенса требованием не
становится). Относительный путь считается от корня проекта и не может
выйти наружу; абсолютный берётся как передан.
Нет файла или секции — отказ ДО создания TODO, `.ready` и baseline.

Почему: требование первоисточника всплывало только на ревью (кейс 0218);
чек-лист в TODO делает его видимым исполнителю с первого шага.

## Пакет спецификации (spec_package)

Юнит разработки может объявить пакет нормы — каталог внутри проекта с
шестью документами (контекст, требования, ревью требований, архитектура,
тестовая спецификация, готовность):

```yaml
---
spec_package: docs/spec/spec-pipeline
source_refs:
  - docs/spec/spec-pipeline/spec-pipeline.md#R3 — Гейт готовности на входе в разработку
  - docs/spec/spec-pipeline/spec-pipeline.md#R4 — Передача нормы в implementer
---
```

- `spec_package` — путь от корня проекта. Абсолютный путь и `..` — отказ.
- `source_refs` — минимум одна ссылка `<файл>#<секция>` внутрь пакета.
  Секция — точный заголовок целиком (`#R3` не найдёт `### R3 — …`);
  матрица покрытия называет её токеном, ссылка может быть полнее. Файл,
  секция и уникальность заголовка проверяются до любых побочных
  эффектов; пустое тело секции — отказ с локатором. Ссылка обязана
  покрывать хотя бы одну строку матрицы покрытия, иначе отказ.
- Гейт готовности — один предикат для трёх точек: создание юнита
  (`dispatch_todo`), старт и продолжение (`start_pipeline`,
  `continue_pipeline`). Пакет обязан быть `READY`, вердикт — `PASS` на
  текущей ревизии требований, отпечаток `Пакет-sha` — совпадать, матрица
  — полной. Отказ не оставляет TODO, baseline, lease, PID и стадии;
  повторный вызов даёт тот же текст.
- Производитель и потребитель: юнит с `spec_package` и пайплайном
  `spec`/`spec-<slug>` — производитель пакета, гейт его не проверяет
  (этот прогон и делает пакет `READY`); снимок нормы такой юнит не
  получает. Остальные юниты с `spec_package` — потребители и проходят
  гейт.
- `Статус: BLOCKED` в документе готовности возвращает пакет автору
  (требования или архитектура) как `FAIL` ревью — без ручного kill.
- В TODO попадает снимок нормы: раздел `## Пакет спецификации` (путь,
  `Пакет-sha`, ревизии шести документов, все ID матрицы, остаточные
  риски) и по разделу `## Первоисточник (<секция>)` на каждую ссылку в
  объявленном порядке. Тело секции вставляется как есть, без пересказа.

Ключи `spec_package` и `source_refs` — пара: пакет без ссылок и ссылки без
пакета отклоняются валидацией контракта. Исключение — производитель пакета
(пайплайн `spec*`): он пишет пакет, поэтому ссылки ему не нужны. Юнит без
`spec_package` живёт по прежним правилам, старый параметр `source_ref`
продолжает работать.

Бюджет объёма пакета: документ — 2200 слов, пакет — 11000. Счётчик —
`awk '{n += NF}'` по файлу целиком, включая заголовки и таблицы. Ключи
`spec.budget.document` и `spec.budget.package` в `.agentic/config.yaml`
переопределяют умолчания. Превышение — MAJOR, `READY` не выдаётся.
`awf verify-pack` печатает секцию `spec_budget` как справку: она не
останавливает стадию и не мешает коммиту, готовность проверяют только
три точки входа (создание, старт, продолжение).

## Границы записи стадии (output / write_allow)

Стадия пайплайна может объявить один артефакт `output` и дополнительные
разрешённые пути `write_allow`. Allowlist стадии = `output` ∪ `write_allow`.
Загрузчик требует: оба пути — от корня проекта, без `/` в начале и без
`..`; `output` не внутри `.git/` и (кроме служебного кандидата
`.agentic/roles/draft/`) не внутри `.agentic/`; `write_allow` — не внутри
`.agentic/` и `.git/` и только внутри каталога своего `output`. Проверка
записи включается у любой стадии, объявившей `output` или `write_allow`.
Единственный обход — явный ключ `write_check: "off"`, названный прямо в
пайплайне (его несёт служебный забег создания роли: рабочий пишет
кандидата и файлы проекта, поэтому `output` не покрывает его записи).
Тихого обхода нет.

Движок снимает манифест дерева до и после стадии (sha256 изменённых
отслеживаемых и новых неигнорируемых файлов). Путь вне allowlist — стадия
переходит в `BLOCKED` даже при сигнале `DONE`: пишется
`.agentic/context/STAGE-DIFF-<todo>-<stage>.md` со списком путей, файл
остаётся в дереве, коммита нет, откат не выполняется. Сбой снятия
манифеста (нет git, таймаут) — тот же `BLOCKED`, а не пропуск проверки.
Служебные каталоги `.agentic/` (`paths.RUNTIME_DIRS`: `outbox`, `inbox`,
`state`, `logs`, `context`, `handoff`, `done`, `dashboards`, `inputs`,
`roles/draft`) не считаются записью стадии.

Нарушение переживает попытку: движок пишет
`.agentic/context/WRITE-VIOLATION-<todo>.json` и `outbox/BLOCKED-<todo>.md`
(со ссылкой на `STAGE-DIFF`), а `last_signal` становится `BLOCKED-<todo>`.
Пока запись открыта, `build_commit_plan` отказывает любому коммиту; ACK или
повтор стадии её не снимают. Новое нарушение по тому же юниту дополняет
запись, а не заменяет её: отказ по первому забракованному пути остаётся.
Нарушение закрывается, когда забракованный путь откатили или переписали,
либо когда запись удалили вручную (явное снятие).

Состояние `after` в записи — sha256 (64 hex) содержимого забракованного
пути после стадии. Маркер `<missing>` означает «файла уже не было при
записи»; это легальное значение для `file_hash`, но не доказуемое
состояние для гейта: по нему нельзя проверить, что забракованное
изменение ушло. Поэтому любое значение `after`, не являющееся 64-hex
(включая `<missing>` и `null`), держит запись открытой — fail-closed. Снять
такую запись можно только явным удалением файла, как и запись без путей.

Запись не предотвратить: `bash` доступен роли, поэтому обещание механизма
— «путь назван и не попал в коммит», а не «файл не изменён».

`files:` в контракте dev-юнита — другой механизм: это отчёт о заявленных
файлах для `verify-pack` и находка при расхождении с diff. Он не запрещает
коммит и не становится allowlist стадии.

## Условный запуск стадии (skip_if)

Ключ стадии `skip_if` — единственный способ пропустить стадию по вердикту.
Допустимо одно значение — `checklist_green`: стадия выполняется, только
если гейт чек-листа юнита красный. Нет ключа или `null` — стадия идёт
всегда, гейт на границе не вызывается. Любое другое значение (опечатка,
пустая строка, число, `bool`) — ошибка загрузки и записи пайплайна: текст
называет стадию и значение, стадия не стартует. Ключ общий; в этой
итерации его ставит только `implementer-close`, и он требует рядом
`write_check: "off"` (закрыватель не объявляет `output`). Значение
сохраняется в обоих снапшотах пайплайна — per-TODO и служебного забега.
В снапшоте служебного забега `skip_if` снимается у стадии, чей `output`
заменён ролью-кандидатом: решение о пропуске принадлежало старому выходу,
а кандидата создаёт именно эта стадия.

### Точка решения

Точка решения есть только у agent-стадий: гейт чек-листа запускается на
входе `execute_agent_stage` со `skip_if`, на текущем дереве.
Supervisor-стадия ключ не читает и идёт всегда. Ключ не ставят на первую
стадию (`plan`) и на последнюю стадию пайплайна. В штатных пайплайнах
последняя — `verify`; если же последней стоит воркер, его пропуск обошёл
бы проверку объявленного выхода, а прогон закончился бы без `verify` и
без коммита. Загрузчик такой позиции не запрещает (ключ допустим на любой
стадии) — ограничение держит автор пайплайна. Гейт пишет одну строку
в лог: `dod: N/M`
(N — пункты `ok`, M — все), при непустых списках добавляются
` (missing: id,…)` и ` (manual: id,…)`; `dod: none` — блока нет;
`dod: 0/0 (missing: (empty block))` — блок пуст. `manual`-пункты closer
не запускают.

Зелёный вердикт (`status=none` или `ok=true`) — стадия пропускается:
воркер не спавнится, PID не остаётся, в state пишутся `stage_skipped=true`
и `stage_skip_reason="checklist_green"`. Оба поля сбрасываются одним
местом — на старте следующей стадии в оркестраторе. Красный вердикт —
запуск closer. Статический дефект блока (пустой или нечитаемый) и
статический дефект стадии (`skip_if` без `write_check: "off"`) дают
`BLOCKED` без запуска closer и без траты бюджета: в `outbox` появляется
пара `BLOCKED-<id>.md` + `BLOCKED-<id>.ready`, поэтому юнит закрыт для
`is_closed`, `blocked_count` и ожидания событий. `unblock` уносит пару
в `context/`, и юнит снова активен.

Первый вердикт юнита лежит в `context/CLOSER-<todo>.json`: `todo_id`,
замороженная `wave`, `first_verdict` (вердикт точки решения — до closer)
и `attempts`. На первом красном решении до спавна туда же пишется
`before` — снимок нормы: хэш блока чек-листа и хэш ключей контракта
`verify`, `gates`, `prove_red` (`files` и остальные ключи не входят).
После завершённого прогона движок сверяет норму с этим снимком, а не с
предыдущей попыткой: правка блока или замороженных ключей контракта даёт
`BLOCKED` «closer edited the checklist/contract» с именем изменённой
поверхности, даже если пункты закрыты. Файл при этом не откатывается
(доктрина 02), коммита нет. Ручной `awf checklist check` и verify-pack
этот файл не создают и не меняют. Битый файл — `BLOCKED`, молча не
перезаписывается.
`--force`-перевыпуск того же номера удаляет `CLOSER-<todo>.json` и
пересоздаёт baseline: это другой юнит со своей историей и своим бюджетом.

Бюджет попыток — `checklist.closer_attempts` в `.agentic/config.yaml`:
целое от 1 до 2, по умолчанию 1. Попытку тратит завершённый прогон closer
с вердиктом; падение без сигнала, salvage и зелёный пропуск бесплатны.
Неверное значение (ноль, три, строка, пусто) — `BLOCKED` с именем ключа
до спавна, без подмены дефолтом.

Счётчики по первым вердиктам отдаёт `awf checklist stats [--wave W]
[--json]`: на пункт — `caught` (юнитов, где пункт попал в `missing`) и
`runs` (юнитов, где пункт проверялся). `manual` не считается; без данных
печатается только заголовок таблицы.

## Dispatch baseline: таймаут и журнал (RB-4)

Снимок baseline при `dispatch` — дымовая проверка, а не ворота. Команда
`verification.baseline_cmd` (или `test_cmd`, если первой нет) получает
собственный таймаут: ключ `verification.baseline_timeout` в
`.agentic/config.yaml`, по умолчанию 60 секунд. Зависшая команда
убивается вместе с группой процессов; в `BASELINE-<id>.tests.log`
пишется `timed out after <T>s`, а юнит всё равно выдаётся: md, baseline и
`.ready` на месте. Супервизор видит `baseline_test_status`
(`timeout` / `skipped` / `passed` / `failed`) и `baseline_timeout` в
ответе dispatch.

`awf dispatch --no-baseline-tests` (MCP:
`awf_dispatch_todo(..., no_baseline_tests=True)`) не запускает команду
вовсе: sha/status/env снимаются, в логе `skipped`, `.ready` ставится
сразу. Для проектов, где baseline-команда медленная по своей природе.

Dispatch журналируется: журнал попытки с телом TODO пишется до
резервирования id и публикуется как `context/DISPATCH-<id>.json` после
победы в резервировании; удаляется сразу после `.ready`. Обрыв
процесса посреди baseline оставляет журнал — юнит можно завершить
командой `awf dispatch --resume TODO-NNNN` (без повторной выдачи):
недостающий/пустой md восстанавливается из журнала, baseline
переснимается, `.ready` ставится, журнал удаляется. Обычная ошибка
чистит и md, и журнал — частичного TODO не остаётся. Журнал хранит
только тело TODO: если dispatch нёс exclusions (`carry_over_from`,
`include_untracked`, `claim_from`), `--resume` отказывает — baseline
пришлось бы пересобрать без этих исключений. Такой юнит перевыпускают
через `--force`, а не резюмируют.

Повторный dispatch того же явного id по-прежнему отказывает и старый
TODO не перезаписывает. `--force` (MCP `force=True`) разрешает
перезапись явного id для перевыпуска юнита; при живом пайплайне отказ,
старый `.ready` снимается до пересборки baseline.

## BLOCKED-заметка (стандартная схема)

Заблокированный юнит пишет `outbox/BLOCKED-<id>.md` (рядом с сигналом
`BLOCKED-<id>.ready`). Заголовки фиксированы — по ним супервизор и
`awf blocked-draft` (`awf_blocked_draft`) собирают черновик REVIEW-фикса:

```markdown
## ВЕРДИКТ

blocked — одна строка: почему юнит не может продолжаться.

## НАХОДКИ

- <что найдено, с file:line>
- <…>

## НАПРАВЛЕНИЯ-ФИКСА

- <что сделать, чтобы разблокировать>
- <…>

## ПЕРЕНОСЫ

- <что сознательно уходит в другой юнит / бэклог; «нет», если пусто>
```

Правила:

- только `## ` (уровень 2) и точные имена: `ВЕРДИКТ`, `НАХОДКИ`,
  `НАПРАВЛЕНИЯ-ФИКСА`, `ПЕРЕНОСЫ`. Подзаголовки глубже (уровень 3+)
  остаются внутри своей секции;
- `НАХОДКИ` и `НАПРАВЛЕНИЯ-ФИКСА` — списком: каждая находка/направление
  отдельным пунктом с локацией;
- заметка без `НАХОДКИ` и `НАПРАВЛЕНИЯ-ФИКСА` считается не по схеме —
  `awf blocked-draft` откажет. Отказ — не ошибка юнита: чинится заметкой,
  сигнал BLOCKED при этом остаётся;
- `awf blocked-draft TODO-NNNN` печатает готовый текст `## REVIEW-фикс` с
  пустыми слотами решений супервизора (`Скоуп: …`, `Переносы: …`) и НЕ
  пишет в TODO — вставку и решения оставляет за супервизором.

Почему: кейс 0218 — два требования первоисточника нашлись только на
пятом часу, а каждый виток супервизор вручную переписывал заметку в
REVIEW-фикс. Фиксированная схема делает этот шаг механическим.

## Перенос отклонённого юнита (carry_over_from)

При повторной выдаче отклонённого юнита супервизор передаёт
`carry_over_from=<id отклонённого>`. Перенос берёт ровно два набора
путей из `REJECT-<id>.files`:

- новые неотслеживаемые файлы попытки — untracked сейчас минус снимок
  `BASELINE-<id>.untracked` на момент выдачи;
- отслеживаемые пути, которые изменила попытка, — текущие изменения
  минус грязный набор baseline. Предсуществующая чужая работа в этот
  набор не попадает. Предсуществующий untracked-файл, который попытка
  просто заиндексировала, тоже чужой: untracked-снимок baseline —
  второй источник чужих путей, как и в плане коммита.

У переименования переносятся обе стороны пары, у копии — только новый
файл: источник копии git выбирает по похожести, это не правка попытки.
Gitignored-файлы тоже не попадают — git их не отслеживает.

Если у отклонённого юнита нет `BASELINE-<id>.status` (старый или
самодельный baseline), грязный набор до выдачи неизвестен: tracked-дельту
тогда не записывают и не переносят — иначе в неё попала бы любая чужая
правка из дерева. Untracked-часть переносится как обычно.

Пути из переноса исключаются из `BASELINE-<retry>.untracked` и получают
владение в плане коммита: tracked-изменение входит в кандидата и коммит
повторного юнита целиком, даже если baseline повтора снят на уже
грязном дереве. SHA baseline при этом не двигается — base-commit не
нужен.

Цепочка повторов не теряет перенос: baseline повтора снят на дереве
предшественника, поэтому его пути сидят в грязном наборе повтора. Их
считают своими (юнит их принял), и повторный reject записывает их в свой
`REJECT-<retry>.files`. Иначе вторая попытка осталась бы без tracked
дельты, а следующая по цепочке молча выкинула бы её из коммита.

Без `carry_over_from` поведение прежнее: tracked-изменения, которые были
в дереве до выдачи, считаются чужими и в коммит юнита не входят.

## DONE.json

Исполнитель может (не обязан) писать `.agentic/outbox/DONE-<id>.json`:

```json
{
  "files_changed": ["awf/unit_contract.py", "tests/unit/test_unit_contract.py"],
  "tests_run": [
    {"cmd": "python3 -m pytest tests/unit/test_unit_contract.py -q", "result": "38 passed"}
  ],
  "gates": ["contracts", "ratchet"],
  "notes": "коротко, что важно для следующей роли",
  "stage": {"stage_id": "impl", "attempt": 1}
}
```

Схема (все ключи необязательны): `files_changed: [str]`,
`tests_run: [{cmd: str, result: str}]`, `gates: [str]`, `notes: str`,
`checklist: {id: bool}` или `checklist_checked: [id]` — заявления по
чек-листу (проверяются прогоном, расхождение — warning),
`stage: {stage_id: str, attempt: int, role: str, model: str}` — блок
идентичности стадии, под-ключи внутри него тоже все необязательны
(ORCH M4.3). Старый файл без блока работает ровно как раньше.

`stage` — идентичность стадии. Worker получает её в промпте (строка
«Stage identity»: stage_id/attempt/role), так что блок — копия
данных, а не угадывание. Битый json или нарушение схемы (в том числе в
блоке `stage`) — предупреждение в `orchestrator.log`, файл пропускается,
пада нет.

Движок при сборке handoff (`awf/agent_stage.py::collect_handoff`) включает
валидный файл в секцию «Machine facts (DONE.json)» handoff-файла следующей
роли. Независимо от DONE.json handoff всегда несёт ЕДИНУЮ секцию
«Stage facts»: stage_id/attempt/role и model, если он известен из
конфига, — движок заполняет её сам, из стадии и счётчика ретраев, — плюс
метаданные прогона (время генерации, exit code, длительность, сигналы,
изменения к baseline) и факт `DONE-json=present/absent` в строке
«worker notes». Если в DONE.json есть блок `stage`, секция получает строку
сверки (matched/mismatched — пометка для следующей роли, не ошибка).
Секция «DONE summary (from worker)» — дайджест (первые 10 непустых строк
отчёта) и ссылка `full report: .agentic/outbox/DONE-<id>.md`; полная
вклейка отчёта в handoff убрана (0187).

Секция «Engine facts» — факты движка, которых нет в DONE.json воркера
(файл принадлежит воркеру и ручной прогон снаружи движка не видит).
Сейчас там один факт: `suite_gate=raw-full-suite` — в логе воркера был
полный прогон (`pytest tests/` или `scripts/run-all.sh`), а канонического
артефакта `.agentic/context/SUITE-<tree-sha>-*.json` с командой из
`awf suite-command` нет. Стадию и коммит факт не блокирует. Старые handoff
без этой секции читаются как раньше.

Пустой `pytest` без позиционной цели считается полным прогоном, когда в
конфиге pytest объявлен непустой `testpaths`; ключи `-k`/`-m` его полноту
не отменяют, только сужают набор внутри. Редирект (`2>&1`, `> файл`) и
значение опции (`--timeout 600`) целью не считаются. Позиционная цель —
только путь (разделитель, ведущая точка, файл `.py`) или node-id
(`файл.py::test`), поэтому значение неизвестной опции (`--cov awf`,
`--junitxml report.xml`) полноту не отменяет.

С явной целью селекторы ведут себя по-разному: `-k` сужает прогон
(`pytest tests -k smoke` — не полный), а `-m` нет (`pytest tests -m slow`
остаётся полным). Так R13 и говорит: полным не считается только явный файл
или `-k`; для `-m` выбираем более громкую сторону — лишнее предупреждение
вместо пропуска. Остаток принимаем осознанно (AUD-28-13).

Обёртки перед раннером снимаются вместе со значениями своих опций:
`timeout -k 5 300 pytest tests/`, `env -u FOO pytest tests/` и
`bash -lc 'pytest tests/'` видны как полный прогон. Значение `env -S`
(целая командная строка) не разбирается. Служебные слова оболочки перед
раннером (`then`, `do`, `else`) и `sudo` тоже снимаются: `if …; then
pytest tests/` и `for …; do pytest tests/` — полный прогон.

Та же цель в другой записи — тоже полный прогон: `pytest .`, `./tests`,
`./tests/`, `tests/.`, `$PWD/tests`. `./tests/unit` и явный файл остаются
узкими.

Разбор команд для трёх потребителей один — `awf/command_parse.py`
(AUD-27-3): гейт, флейк-проба verify-pack и `scripts/suite-canonical.sh`
зовут его, а не держат свои парсеры. Перед раннером снимаются префиксы
`uv run`, `poetry run`, `pdm run`, `hatch run` (вместе со значением опции;
матрица hatch `+py=3.12` и форма окружения `test:pytest`/`test:python -m
pytest` — не программа: имя программы после последнего `:`), и обёртки `timeout`, `env`,
`sudo` (вместе со значением их опции), `cd`/`pushd`, `command`, `exec`,
`nohup`, `setsid`; `awf suite-command --runner="<команда>"` печатает имя
раннера для артефакта тем же разбором (этот режим всегда отвечает 0 и
проектный конфиг не читает). Неизвестный boolean-флаг раннера перед формой
окружения — флаг, а не опция со значением: `hatch run -v test:pytest
tests/` считает следующее слово программой по хвосту после `:` (AUD-28-15).
Если снятая обёртка оставила
скрипт (`uv run scripts/run-all.sh`), имя раннера — `unknown`: счётный
формат скрипта неизвестен, и `uv` не выдаётся за него. Обёртка без
снятия (`bash scripts/run-all.sh`) пока называет раннером `bash` —
известный остаток AUD-28-11, follow-up.

Ограничение эвристики: строка печатного вывода без маркера `$ ` может
дать ложный `SUITE-WARN:`. Граница шире `cat`-листингов: непромптовая
печатная строка, которая начинается словом-раннером и называет цель
(`pytest tests/`, `bash scripts/run-all.sh`), — полный прогон, даже если
это докстринг, вывод `cat` или эхо чужой команды. Пустой `pytest` без
цели попадает сюда только при объявленном `testpaths`. Единственный
признак выполненной команды — `$ `-промпт. Ложную тревогу оставляем
намеренно — R13 предпочитает её пропуску сырого прогона.

Коды возврата `awf suite-command` (режим команды): 0 — команда из `verification.test_cmd`,
1 — легаси-фолбэк (ключа нет), 2 — ключ пустой или `null`, 5 — битый
`.agentic/config.yaml`. Код 5 стоит отдельно: нечитаемый файл — не
пустой ключ, и легаси-pytest для него не безопасен. Скрипт
`scripts/suite-canonical.sh` отвечает на код 5 текстом «broken
.agentic/config.yaml».

Отчёт на стадии verify: `.agentic/context/GATES-<todo>.md` (собирает
`awf verify-pack --todo <id>`, U5) — быстрые гейты, safety-канарейки,
минимальность диффа против baseline, команды из `verify:`, prove-red и
`ruff check .`; полный сьют туда не входит (он у QA). Тумблер
`automation.verify_pack` в `.agentic/config.yaml` (дефолт true). Отчёт
остаётся в `context/`: `archive_todo` переносит только inbox/outbox,
`GATES-<id>.md` он не трогает.

## QA-файл находки (verify_pack)

Когда QA-стадия находит дефект, она кладёт воспроизводящий тест в
`.agentic/context/QA-<NNNN>-findings-test.py` — канон имени без префикса
`TODO-` (полная форма `QA-TODO-<NNNN>-findings-test.py` тоже читается).
Читатель один — `awf/verify_pack.py::_qa_findings_path` (канон побеждает,
если лежат оба имени).

- **Формат:** модуль pytest с функциями `test_*`, не голый скрипт.
  Verify-pack запускает его как
  `<python> -m pytest <файл> -q --timeout=<таймаут секции>
  -p awf._safety_tripwire`, один раз, без проверки на флейки. Флаг
  `--timeout` ставится только при доступном плагине `pytest-timeout`;
  без него работает собственный wall-clock таймаут раннера (процесс
  убивается по группе). Плагин
  `awf._safety_tripwire` ставит tripwire сессии: файл лежит вне `tests/`,
  и без него естественный repro вида `os.killpg(1, 15)` убил бы всю
  сессию пользователя.
- **Ручной прогон:** только через verify-pack или с тем же плагином
  (`python -m pytest -p awf._safety_tripwire <файл>`). Голый
  `pytest <файл>` не защищён.
- **Вес:** секция `qa_findings` — как контрактный тест. Файла нет —
  `none` (не измерено); зелёный — `pass`; красный или таймаут — `fail`,
  вердикт пакета `failed`; pytest недоступен — явная ошибка секции, не
  `pass`.
- **После приёмки:** файл остаётся в `context/` как evidence попытки, в
  коммит юнита не входит (context — рантайм). Удаляется вручную при чистке
  или вместе с архивом рана; сам QA-файл verify_pack не трогает.

## Матрица замыкания (ФС-границы)

Если блок `## Границы` юнита (`inbox/TODO-*.md`) называет разрушающую или
пишущую ФС-операцию — `unlink`, `rmtree`, `move`, `replace`, `write_text`
или `mkdir` — юнит обязан нести секцию `## Матрица замыкания` с таблицей:

| Операция | Поверхность | Корень/лист | Порядок |
|---|---|---|---|
| что делаем | где (файл/каталог) | проверяем корень или лист | когда проверка относительно эффекта |

Считается только токен в бэктиках: глагол в прозе («replace старую
проверку») операцией не является и матрицы не требует.

`scripts/check-contracts.sh` проверяет это для живых юнитов и краснеет на
отсутствующей таблице. Архивные контракты (`done/`) не читаются — правило
сторожит планы в работе, а не историю.

Почему: без таблицы «поверхность × исход» половина клеток остаётся
непроверенной — симлинк на одной поверхности обходит барьер, поставленный
на другой.

## Переезды и удаления файлов

Переезд — обычным `mv`, удаление — `rm`; не `git mv` / `git add` /
`git rm`.

Почему: git-команды стейджат, а коммит-гейт R-03 считает
staged-против-baseline WIP владельца и исключает такие файлы из
коммита юнита. Переезд через git тихо выпадает из коммита (инцидент
8.1, волна 8.4: переезд трёх доков через `git mv` не попал в коммит
юнита; супервизор снял стейджинг, фиксация — отдельным юнитом).
