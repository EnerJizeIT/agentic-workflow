# Контракт юнита (U3)

Необязательный машиночитаемый контракт по TODO: план-stage объявляет, что и
как проверять, исполнитель отчитывается машиночитаемыми фактами вместо прозы.
Всё необязательно — TODO без блока и DONE без json работают ровно как раньше.

## Блок в TODO (front-matter)

В самом верху TODO-файла, между двумя строками `---`. Строки-комментарии
`<!-- ... -->` (например role hint, который добавляет dispatch) до блока
пропускаются. Заголовок `# TODO — <название>` тоже может стоять выше блока:
контракт, записанный сразу под заголовком, читается так же (пропускается
ровно один заголовок первого уровня; горизонтальная черта дальше в теле
блоком не считается).

```yaml
---
verify: ["python3 -m pytest tests/unit/test_x.py -q"]
gates: ["contracts", "ratchet"]
prove_red: ["tests/unit/test_x.py::test_y"]
---
# TODO-0001 — задача

тело…
```

Ключи (все необязательны, но объявленный ключ обязан быть заполнен):

- `pipeline` — имя пайплайна для запуска в забеге (строка, не список).
  Когда `awf_run_next` запускает TODO без пайплайна на уровне очереди
  забега, он берёт имя отсюда (RUN3 #2). Имя — как у пайплайнов: буквы,
  цифры, `_`, `.`, `-`; пустое имя не принимается (пусто = пайплайн из
  config, ключ просто не пишут). `awf_dispatch_todo(..., pipeline=...)`
  пишет ключ в блок автоматически (блок создаёт, если его нет).
- `replan_for` — маркер replan-ответа (BD-30, TODO-0213): id юнита,
  которого заменяет этот TODO (строка, `TODO-NNNN`). Replan-вейт
  (интерактивный `wait_for_supervisor_signal` И auto-субпроцесс —
  watcher с фильтром и fallback-детектор; kind="replan") подхватывает
  свежий TODO как ответ супервизора только при маркере, называющем
  эскалированный юнит; обычный mid-run диспатч без маркера живой
  пайплайн не трогает. Без маркированного ответа пайплайн
  останавливается на заблокированном юните (BLOCKED остаётся;
  dispatch с маркером + `awf continue` продолжает).
  `awf_dispatch_todo(..., replan_for=...)` пишет
  ключ в блок (блок создаёт, если его нет); ручная строка в блоке
  работает так же. Референт обязан существовать и быть живым
  (inbox-юнит без DONE-закрытия; архивный или done-юнит — отказ до
  побочных эффектов).
- `verify` — список непустых команд проверки.
  Команды исполняются как argv (без shell), поэтому shell-операторы вне
  кавычек — отказ валидации контракта (диспатч отбивает юнит): `&&`, `||`,
  `;`, `|`, `>`, `<`, фоновый `&`, подстановка команд `$(` и бэктики
  (REVIEW витки 2–3 TODO-0232). Нужна склейка или подстановка — пиши
  скрипт, отдельные команды или цитируй оператор аргументом `sh -c "..."`.
  Окружение задаётся через `env VAR=val команда …` (префикс `VAR=val`
  без `env` — это `argv[0]`, команда не найдётся). Globbing (`a*`) —
  литерал: argv-запуск звёздочку не раскрывает, передавай готовый путь.
  Те же правила действуют для команд из конфига
  (`verification.test_cmd` / `baseline_cmd` etc.): это тот же argv-класс,
  shell-оператор там — отказ, а не молчаливый литерал (REVIEW виток 6
  TODO-0232). Внутренний перевод строки (`\n`, `\r`, `\r\n`) —
  тоже отказ («multi-line verify», REVIEW виток 5 TODO-0232); хвостовой
  `\n` блочного скаляра (`- |`) нормализуется — команда остаётся одной.
- `flake` — переключатель флейк-пробы (M1): `on` (по умолчанию) или `off`.
  Пробуются только тест-подобные команды (`pytest` / `py.test` /
  `python -m pytest`, в том числе через venv-путь) — они выполняются
  дважды. `off` выключает пробу: каждая команда `verify:` выполняется
  один раз.
- `gates` — список коротких имён проверок: канонический набор
  `KNOWN_GATES` из `awf/unit_contract.py`
  (`contracts`, `ratchet`, `instructions`, `tests`, `lint`, `mutations`).
  Это НЕ «имена проверок из run-all.sh»: `scripts/run-all.sh` гоняет
  `contracts`/`ratchet`/`instructions` под этими короткими именами, а
  pytest- и ruff-команды — строками из `scripts/project-commands.txt`
  (это и есть `tests`/`lint`); `mutations` в run-all не входит:
  базовый набор (4 мутации, `scripts/mutations.txt`) гоняется в CI test-job
  отдельным шагом `scripts/mutation-smoke.sh`, а `--report`-прогон
  (`scripts/mutations-neg5.txt`) остаётся ручным шагом. В verify-pack секция
  `gates` исполняет только первые три; `tests`/`lint` покрывают команды
  из `verify:`, а `mutations` — декларация для QA и для CI-базового набора.
- `prove_red` — список тест-идов, которые обязаны быть красными до фикса.
  `awf prove-red --todo <id>` проверяет это машинно (baseline в worktree:
  красный от ассерта + зелёный на текущем дереве; вердикты `red-ok` /
  `not-red` / `broken-runner` / `green-after`) — в отличие от `verify`,
  который просто прогоняет команды проверки на текущем дереве.
- `prove_red_pin` — список тест-идов-щитов: они фиксируют УЖЕ работающее
  поведение, поэтому на baseline обязаны быть ЗЕЛЁНЫМИ. Это противополож-
  ность `prove_red`: там тест обязан падать до фикса, а «зубы» пина (что щит
  реально поймаёт регресс) доказываются мутацией, вне инструмента.
  `prove_red` и `prove_red_pin` взаимоисключимы — оба сразу в одном TODO
  это ошибка контракта. `awf verify-pack` прогоняет пин на baseline: все
   зелёные → вердикт `pin-ok` (секция pass, не fail, с пометкой «регресс-щит;
   зубы вне автоматики»); КРАСНЫЙ на baseline → `fail` (это не пин, а находка
   — тест падает на старом коде); ошибка коллекции → `broken-runner`.
- `prove_red_kind` — объявленный тип prove-red-проверки (строка). Два типа:
  - `coverage` — юнит-покрытие/валидация: его тесты проверяют
    поведение, внедрённое РАНЕЕ (в других юнитах), поэтому на baseline этого
    юнита они зелёные по построению, и prove-red честно вернёт `not-red`.
    С объявленным kind вердикт `not-red` — PASS секции `prove_red` в
    verify-pack с пометкой «coverage unit — not-red is expected (declared)»
    и записью `prove_red_note` в отчёт, а не провал.
  - `new-api` — юнит нового модуля/символа: тест падает на baseline только
    потому, что символа ещё нет (prove-red помечает такую причину типизированным
    фактом `new_code_acceptable`, а не текстом предупреждения). С объявленным
    kind этот вердикт — `new-api-ok`: PASS с предупреждающей секцией, exit-код
    verify-pack остаётся 0. Настоящая поломка раннера (ошибка коллекции вне
    проекта, 0 тестов, таймаут) остаётся fail.

  Остальные вердикты (`red-ok` — pass как раньше, `green-after`/реальный
  `broken-runner` — fail) и все прочие секции объявлением не затрагиваются.
  Kind требует `prove_red` (тип модифицирует именно эту проверку) и
  `prove_red_note`; взаимоисключим с `prove_red_pin` (оба ждут зелёный на
  baseline, но по разным причинам — объявленное покрытие против
  регресс-щита).
- `prove_red_note` — обоснование для `prove_red_kind` (непустая строка),
  записывается в GATES-отчёт. Ключи — пара: объявление одного без другого
  — ошибка контракта.

Пример coverage-юнита:

```yaml
---
prove_red: ["tests/test_presets.py"]
prove_red_kind: coverage
prove_red_note: "поведение пресетов внедрено в U2; этот юнит только добавляет покрытие"
---
```

Без объявления `not-red` не смягчается (останется провалом), но если дифф
юнита — только тестовые пути (никаких правок исходников), verify-pack
добавит в GATES-отчёт строку-подсказку объявить
`prove_red_kind: coverage` + note. Это подсказка, не автоподмена
вердикта.

Валидация в `awf/api/dispatch.py::dispatch_todo` (один путь для MCP и CLI):

- блока нет — не ошибка;
- битый YAML, ключ не-списком, пустой список, пустая строка в списке,
  неизвестное имя gate — `AwfApiError` с текстом, что именно не так и как
  правильно;
- неизвестный ключ в блоке (опечатка) — не ошибка, но предупреждение в
  `pre_check_warnings` ответа dispatch.

- `checklist_classes` — список классов проверок завершения (строки,
  непустой список). Классы объявлены явно: неизвестный класс — отказ
  диспатча, дубли id между базой, классами, волной и приёмкой — тоже
  отказ. Подсказки по разделу «Границы» печатаются строкой
  `checklist_suggested:` и сами не мержатся (TODO-0244); объявленный
  класс в подсказки не попадает.
- `wave` — имя волны (слаг: буквы, цифры, `_`, `.`, `-`). Волна лежит в
  `<project>/.agentic/checklists/waves/<name>.yaml` и добавляет свои
  пункты в чек-лист юнита. Пропущенный файл волны — отказ диспатча,
  ключ просто не пишут для одиночного юнита (TODO-0244).

## Чек-лист завершения (DoD)

При диспатче в TODO дописывается блок `## Чек-лист завершения`: базовый
набор + объявленные классы + пункты волны + приёмочные пункты юнита
(секция `## Приёмка`, по одному на строку). Блок фиксируется в файле:
правка волны посреди юнита живой юнит не меняет. Строка блока:

```
- [ ] <id>: <text> — probe(<type> <args>) expect <...>
- [ ] <id>: <text> — probe(command_rc timeout=<n> <argv>) expect rc=<n>
- [ ] unit-01: <критерий приёмки> — manual
```

Однострочный текст пишется как есть; многострочный, с краевыми пробелами
или неоднозначный (кавычка в начале, ` — probe(` внутри) — JSON-строкой,
чтобы перевод строки, кавычки и юникод пережили заморозку и разбирались
ровно тем же значением. Аргументы пробы пишутся одним JSON-массивом
(`["git", "status"]`) и читаются обратно тем же разбором: табуляция,
перевод строки и кавычки в шаблоне не превращаются в текст эскейпа.
Старые блоки с shell-цитированием читаются как есть.

`manual` — пункт без пробы, его проверяет принимающий; гейт такие пункты
не считает проваленными.

Разбор блока не теряет пункты. Читается любой маркер списка (`- [ ]`,
`* [ ]`, `+ [ ]`, голый `[ ]`) и отступ: пункт — это пункт, а не проза.
Строка, которая похожа на чекбокс, но не разбирается, — ошибка, а не
пропуск. `expect` у `grep_*`/`file_*` — строго `present` или `absent`:
опечатка не инвертирует проверку молча. Заголовок блока без пунктов —
провал (`(empty block)`), а не пройденный чек-лист; «блока нет» и «блок
пуст» — разные факты. Путь пробы (`file`, `path`) проверяется, как
позиционный аргумент `command_rc`: при загрузке данных и при разборе
блока он не может выйти за корень проекта, а на прогоне такой пункт
падает сам, не обрывая остальные.

Таймаут пробы живёт в блоке: у `command_rc` необязательный
`timeout=<n>` стоит сразу после типа пробы и применяется при прогоне.
Значение по умолчанию — 120 секунд (потолок схемы), поэтому в строке
его не пишут. Блок — единственный источник, который исполняет гейт,
так что объявленный в YAML таймаут переживает заморозку, а не
подменяется потолком.

Гейт исполняет пробы и пишет `context/CHECKLIST-<todo>.json`, привязанный
к отпечатку дерева. Отпечаток дерева не видит `.agentic/` (каталог в
`.gitignore`), а базовые пробы читают именно его, поэтому ключ кэша
включает ещё и цели проб: содержимое для читающих проб и факт наличия для
`file_*`. Тот же ключ и тот же блок — переиспользование, изменился ключ —
пересчёт. Заявления из DONE.json (`checklist` /
`checklist_checked`) — не истина: расхождение с прогоном даёт warning.

`awf checklist show <todo>` печатает блок, `check` — вердикт и пропуски
(rc 0/1), `hash` — sha256 ровно блока, `apply` — пересобирает блок у уже
задиспатченного НЕ начатого юнита (та же композиция и та же проверка
читаемости, что при диспатче; бэкап, идемпотентно; начатый или
архивный — отказ). Подробности и правила обновления —
`docs/design/dod-gate.md`.

## Первоисточник (source_ref)

`dispatch_todo(..., source_ref="<файл>#<секция>")` (CLI:
`awf dispatch --source-ref`) вставляет в TODO раздел первоисточника сразу
после заголовка `# TODO-NNNN` (контрактный блок остаётся первым, заголовок —
первым заголовком: по нему работают защиты номера):

```markdown
# TODO-0001 — юнит

## Первоисточник (R2.5)

- [ ] владелец один
- [ ] второй пункт
```

Секция ищется по точному тексту заголовка (без fallback по первому слову);
два заголовка с одинаковым текстом — явный отказ со списком строк. Тело
идёт до следующего заголовка того же или более высокого уровня; пункты
списка (bullets/numbered) становятся чек-листом, продолжения пунктов,
проза и код-фенсы сохраняются как есть (пример внутри фенса требованием не
становится). Относительный путь считается от корня проекта и не может
выйти наружу; абсолютный берётся как передан.
Нет файла или секции — отказ ДО создания TODO, `.ready` и baseline.

Почему: требование первоисточника всплывало только на ревью (кейс 0218);
чек-лист в TODO делает его видимым исполнителю с первого шага.

## BLOCKED-заметка (стандартная схема)

Заблокированный юнит пишет `outbox/BLOCKED-<id>.md` (рядом с сигналом
`BLOCKED-<id>.ready`). Заголовки фиксированы — по ним супервизор и
`awf blocked-draft` (`awf_blocked_draft`) собирают черновик REVIEW-фикса:

```markdown
## ВЕРДИКТ

blocked — одна строка: почему юнит не может продолжаться.

## НАХОДКИ

- <что найдено, с file:line>
- <…>

## НАПРАВЛЕНИЯ-ФИКСА

- <что сделать, чтобы разблокировать>
- <…>

## ПЕРЕНОСЫ

- <что сознательно уходит в другой юнит / бэклог; «нет», если пусто>
```

Правила:

- только `## ` (уровень 2) и точные имена: `ВЕРДИКТ`, `НАХОДКИ`,
  `НАПРАВЛЕНИЯ-ФИКСА`, `ПЕРЕНОСЫ`. Подзаголовки глубже (уровень 3+)
  остаются внутри своей секции;
- `НАХОДКИ` и `НАПРАВЛЕНИЯ-ФИКСА` — списком: каждая находка/направление
  отдельным пунктом с локацией;
- заметка без `НАХОДКИ` и `НАПРАВЛЕНИЯ-ФИКСА` считается не по схеме —
  `awf blocked-draft` откажет. Отказ — не ошибка юнита: чинится заметкой,
  сигнал BLOCKED при этом остаётся;
- `awf blocked-draft TODO-NNNN` печатает готовый текст `## REVIEW-фикс` с
  пустыми слотами решений супервизора (`Скоуп: …`, `Переносы: …`) и НЕ
  пишет в TODO — вставку и решения оставляет за супервизором.

Почему: кейс 0218 — два требования первоисточника нашлись только на
пятом часу, а каждый виток супервизор вручную переписывал заметку в
REVIEW-фикс. Фиксированная схема делает этот шаг механическим.

## DONE.json

Исполнитель может (не обязан) писать `.agentic/outbox/DONE-<id>.json`:

```json
{
  "files_changed": ["awf/unit_contract.py", "tests/unit/test_unit_contract.py"],
  "tests_run": [
    {"cmd": "python3 -m pytest tests/unit/test_unit_contract.py -q", "result": "38 passed"}
  ],
  "gates": ["contracts", "ratchet"],
  "notes": "коротко, что важно для следующей роли",
  "stage": {"stage_id": "impl", "attempt": 1}
}
```

Схема (все ключи необязательны): `files_changed: [str]`,
`tests_run: [{cmd: str, result: str}]`, `gates: [str]`, `notes: str`,
`checklist: {id: bool}` или `checklist_checked: [id]` — заявления по
чек-листу (проверяются прогоном, расхождение — warning),
`stage: {stage_id: str, attempt: int, role: str, model: str}` — блок
идентичности стадии, под-ключи внутри него тоже все необязательны
(ORCH M4.3). Старый файл без блока работает ровно как раньше.

`stage` — идентичность стадии. Worker получает её в промпте (строка
«Stage identity»: stage_id/attempt/role), так что блок — копия
данных, а не угадывание. Битый json или нарушение схемы (в том числе в
блоке `stage`) — предупреждение в `orchestrator.log`, файл пропускается,
пада нет.

Движок при сборке handoff (`awf/agent_stage.py::collect_handoff`) включает
валидный файл в секцию «Machine facts (DONE.json)» handoff-файла следующей
роли. Независимо от DONE.json handoff всегда несёт ЕДИНУЮ секцию
«Stage facts»: stage_id/attempt/role и model, если он известен из
конфига, — движок заполняет её сам, из стадии и счётчика ретраев, — плюс
метаданные прогона (время генерации, exit code, длительность, сигналы,
изменения к baseline) и факт `DONE-json=present/absent` в строке
«worker notes». Если в DONE.json есть блок `stage`, секция получает строку
сверки (matched/mismatched — пометка для следующей роли, не ошибка).
Секция «DONE summary (from worker)» — дайджест (первые 10 непустых строк
отчёта) и ссылка `full report: .agentic/outbox/DONE-<id>.md`; полная
вклейка отчёта в handoff убрана (0187).

Отчёт на стадии verify: `.agentic/context/GATES-<todo>.md` (собирает
`awf verify-pack --todo <id>`, U5) — быстрые гейты, safety-канарейки,
минимальность диффа против baseline, команды из `verify:`, prove-red и
`ruff check .`; полный сьют туда не входит (он у QA). Тумблер
`automation.verify_pack` в `.agentic/config.yaml` (дефолт true). Отчёт
остаётся в `context/`: `archive_todo` переносит только inbox/outbox,
`GATES-<id>.md` он не трогает.

## QA-файл находки (verify_pack)

Когда QA-стадия находит дефект, она кладёт воспроизводящий тест в
`.agentic/context/QA-<NNNN>-findings-test.py` — канон имени без префикса
`TODO-` (полная форма `QA-TODO-<NNNN>-findings-test.py` тоже читается).
Читатель один — `awf/verify_pack.py::_qa_findings_path` (канон побеждает,
если лежат оба имени).

- **Формат:** модуль pytest с функциями `test_*`, не голый скрипт.
  Verify-pack запускает его как
  `<python> -m pytest <файл> -q --timeout=<таймаут секции>
  -p awf._safety_tripwire`, один раз, без проверки на флейки. Флаг
  `--timeout` ставится только при доступном плагине `pytest-timeout`;
  без него работает собственный wall-clock таймаут раннера (процесс
  убивается по группе). Плагин
  `awf._safety_tripwire` ставит tripwire сессии: файл лежит вне `tests/`,
  и без него естественный repro вида `os.killpg(1, 15)` убил бы всю
  сессию пользователя.
- **Ручной прогон:** только через verify-pack или с тем же плагином
  (`python -m pytest -p awf._safety_tripwire <файл>`). Голый
  `pytest <файл>` не защищён.
- **Вес:** секция `qa_findings` — как контрактный тест. Файла нет —
  `none` (не измерено); зелёный — `pass`; красный или таймаут — `fail`,
  вердикт пакета `failed`; pytest недоступен — явная ошибка секции, не
  `pass`.
- **После приёмки:** файл остаётся в `context/` как evidence попытки, в
  коммит юнита не входит (context — рантайм). Удаляется вручную при чистке
  или вместе с архивом рана; сам QA-файл verify_pack не трогает.

## Матрица замыкания (ФС-границы)

Если блок `## Границы` юнита (`inbox/TODO-*.md`) называет разрушающую или
пишущую ФС-операцию — `unlink`, `rmtree`, `move`, `replace`, `write_text`
или `mkdir` — юнит обязан нести секцию `## Матрица замыкания` с таблицей:

| Операция | Поверхность | Корень/лист | Порядок |
|---|---|---|---|
| что делаем | где (файл/каталог) | проверяем корень или лист | когда проверка относительно эффекта |

Считается только токен в бэктиках: глагол в прозе («replace старую
проверку») операцией не является и матрицы не требует.

`scripts/check-contracts.sh` проверяет это для живых юнитов и краснеет на
отсутствующей таблице. Архивные контракты (`done/`) не читаются — правило
сторожит планы в работе, а не историю.

Почему: без таблицы «поверхность × исход» половина клеток остаётся
непроверенной — симлинк на одной поверхности обходит барьер, поставленный
на другой.

## Переезды и удаления файлов

Переезд — обычным `mv`, удаление — `rm`; не `git mv` / `git add` /
`git rm`.

Почему: git-команды стейджат, а коммит-гейт R-03 считает
staged-против-baseline WIP владельца и исключает такие файлы из
коммита юнита. Переезд через git тихо выпадает из коммита (инцидент
8.1, волна 8.4: переезд трёх доков через `git mv` не попал в коммит
юнита; супервизор снял стейджинг, фиксация — отдельным юнитом).
