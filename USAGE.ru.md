# ИСПОЛЬЗОВАНИЕ — Agentic Workflow (awf)

[English](USAGE.md) · [README](README.ru.md)

## Что вы получаете

Структурируйте AI-сессии разработки: план → разработка → проверка → коммит. Supervisor-агент оркестрирует worker-агентов через пайплайн, и вы одобряете каждый результат.

- **Никакого непроверенного кода** — каждое изменение проходит через пайплайн, который вы проектируете: любые роли, любая глубина. От одного воркера до полной цепочки аналитик → архитектор → разработчик → QA → аудит.
- **Полный контроль** — одобряйте или отклоняйте каждый TODO. Отклонение отправляет работу на доработку с инструкцией.
- **Наблюдение в реальном времени** — живой дашборд с handoffs агентов, содержимым TODO, статусом воркера.
- Работает **через чат** — просто скажите что нужно, supervisor вызовет нужный tool.

## Это для вас?

Да, если вы делегируете разработку AI-агентам (opencode) и хотите:
- Quality gates (планирование, ревью, аудит) вместо сырого кода
- Контроль над тем что коммитится
- Структурированный пайплайн с чёткими ролями
- Прозрачность работы агентов

## Старт за 30 секунд

1. **Инициализация** — *"Инициализируй awf в проекте"* → создаётся `.agentic/`, определяется стек.
2. **Цель** — *"Разработать MVP"* → supervisor спрашивает что нужно, открывает форму.
3. **Настройка** — заполните форму в браузере (роли, пайплайн, модели) → *"done"*.
4. **Первый TODO** — supervisor изучает проект, диспетчирует первую задачу, запускает пайплайн.
5. **Мониторинг** — дашборд открывается автоматически. Смотрите как агенты работают.
6. **Проверка** — когда пайплайн достигает verify, скажите *"verify"* → supervisor проверяет, одобряет или отклоняет.

> **Совет:** Не нужно учить названия tools. Просто говорите естественным языком — supervisor сам выберет нужный tool.

## Повседневное использование

| Вы говорите | Что происходит |
|---|---|
| *"Инициализируй awf"* | Создаёт `.agentic/`, определяет стек, спрашивает цель |
| *"Разработать MVP"* | Открывает форму → настраивает пайплайн → планирует TODO |
| *"Продолжи по бэклогу"* | Supervisor читает BACKLOG, проверяет код, диспетчирует след. задачу |
| *"Verify"* | Supervisor читает handoffs + git diff → одобряет или отклоняет |
| *"Отклони — кэш не добавлен"* | Пайплайн остановлен, новый TODO с фиксом |
| *"Остановись после этого TODO"* | Supervisor одобряет текущую работу, ждёт вашего сигнала |
| *"Какой статус?"* | `awf_status` — активные TODO, состояние пайплайна |

## SMO фазы

Awf ведёт supervisor по детерминированному flow:

| Фаза | Вы делаете | Supervisor делает |
|---|---|---|
| **init** | — | Создаёт `.agentic/`, возвращает compact промт |
| **goal** | Отвечаете "что нужно?" | Сохраняет цель, переходит к форме |
| **form** | Заполняете форму в браузере | Открывает форму, рекомендует роли |
| **normalize** | — | Анализирует перекрытия ролей, подтверждает |
| **brief** | — | Изучает проект + BACKLOG, проверяет код, диспетчирует TODO |
| **run** | Смотрите дашборд | **IDLE** — ждёт вашего сообщения |
| **verify** | Говорите *"verify"* | Читает handoffs, проверяет diff, approve/reject |
| **done** | Говорите "продолжай" или "стоп" | Ждёт вашей инструкции |

Каждый tool возвращает `next_action` — подсказку для следующего шага. Даже слабые модели следуют за ней.

**Новая сессия или потерянный контекст** → `awf brief` (MCP `awf_brief`, CLI
`awf brief`, `--json` — машинный вариант). Одна карточка, собранная из ЖИВОГО
состояния, поэтому не прухает: шапка (версия awf, проект, фаза, дата), что
дальше, состояние (забег, активные TODO, blocked/salvage, последний сигнал),
карта инструментов по ситуациям (запуск / проверка / забег / гигиена / формы /
метрики / контекст), ритуалы, рецепты восстановления, что нового. Детерминистично
— при том же состоянии карточка та же (кроме строки даты). Пустому или новому
проекту вместо рабочего цикла отдаётся подсказка setup-цепочки.

## Проверка: approve или reject

| Вы говорите | Что происходит |
|---|---|
| *"Verify"* | Supervisor читает handoffs, проверяет git diff, оценивает качество |
| *"Approve"* (неявно) | Коммитит изменения, архивирует TODO, пайплайн завершается |
| *"Отклони — T8 DOMParser не сделан"* | Останавливает пайплайн, просит диспетчировать TODO с фиксом |
| *"Покажи diff"* | Supervisor выполняет `git diff`, показывает изменения |

**После approve:** пайплайн завершается. Скажите *"продолжай"* для след. TODO или *"стоп"* для паузы.

## Инструменты супервизора (U11): tree-sha, mutations, todo-draft

Три CLI-инструмента для ритуала проверки — ими пользуется супервизор, это не гейты пайплайна:

**`awf tree-sha`** + **`awf approve --verified-sha <hash>`** — «что проверили = что коммитим». На стадии
проверки, ДО своих проб, снимите отпечаток дерева (`awf tree-sha`, MCP: `awf_tree_sha`); после проверок
передайте его в approve (MCP: `awf_approve(verified_sha=...)`). Если дерево изменилось (новый коммит,
правка, новый файл) — approve откажет: «the tree changed after verification». Отпечаток сохраняется в
`.agentic/context/VERIFIED-<todo-id>.sha`. Без `--verified-sha` поведение прежнее.

**`awf mutations [--list]`** — мутационный smoke по `scripts/mutations.txt` на покоящемся дереве (грязное
`git status` → отказ): убитые / выжившие / таймауты с хвостами логов, файлы всегда восстанавливаются.
Ритуал «раз в волну / перед релизом», не авто-гейт каждого юнита.

**`awf todo-draft <AUDIT-ID|FU-NN> [--index PATH] [--out PATH] [--force]`** — скелет файла задачи из реестра
`AUDIT-INDEX.md`: факты (id находок, суть, юнит, файлы) + плейсхолдеры «супервизор дополняет замысел».
Критерии не выдумывает, в сеть не ходит. Существующий `--out` не перезаписывается без `--force`.

**`awf feedback --type bug|feature --title "…" [--body "…"]
[--severity low|medium|high] [--stdout]`** (MCP: `awf_feedback`) —
фидбек-контур: фрикция с awf превращается в отчёт на рабочем столе
владельца (config `feedback.dir`, дефолт `~/Desktop`, каталог
создаётся), файл `awf-<bug|feature>-<YYYYMMDD>-<slug>.md` (тот же день +
тот же слаг → суффикс `-2`, не перезапись). Отчёт собирается сам: факты
(версия awf, проект, фаза, забег — позиция + no_checkpoints, текущая
задача, git sha awf-репо best-effort, дата), скелет «Что пытался /
Ожидал / Что получил / Почему мешает / Предложение» (`--body` идёт в
«Что пытался») и хвост последнего лога (≤20 строк). `--stdout` печатает
отчёт, файл не пишет. Супервизор не молчит: молчание не чинит инструмент.

## Метрики

`awf metrics` (MCP: `awf_metrics`) собирает итоги программы по запросу: токены воркеров (in/out/cache-read)
и компрессии по юнитам из `opencode.db`, токены супервизора по окнам юнитов, строки кода по коммитам
юнитов и конверсию «если бы воркеры работали на модели X» (цены models.dev).

Область (RUN10 #3-fix): по умолчанию собираются только сессии текущего
проекта — сессия относится к проекту, когда её содержимое (`part.data` в
`opencode.db`) содержит путь проекта; `session.directory` — не дискриминатор,
так как воркеры (и супервизор) работают из $HOME. В шапке отчёта строка
«Область: проект: …». Сессии других проектов в дефолтной области исключаются
с честным счётом в предупреждении отчёта, не молча; если путь проекта не
найден ни в одной сессии — пустые данные сессий + предупреждение (явное
«нет данных», а не чужие цифры). `--all-projects` (MCP: `all_projects=True`)
собирает всю общую `opencode.db` (данные смешаны между проектами — поведение
до RUN10).

Markdown-отчёт кладётся в `metrics.output_dir` (по умолчанию `~/Desktop`) как
`awf-metrics-<ГГГГММДД-ЧЧММ>.md`. `metrics.mirror_dir` в `.agentic/config.yaml` — архивная копия каждого
отчёта (ошибка копирования — предупреждение, не сбой); `--no-mirror` отключает копию на один запуск.
Таблица подписок (раздел 💳) обновляется через `awf metrics --refresh-subscriptions`: живой источник
`metrics.subscriptions_url`, при сбое — awf-кэш, затем встроенная таблица.

## Дашборд

Открывается автоматически в браузере при запуске пайплайна:

| Таб | Что видите |
|---|---|
| **💬 Agent Chat** | Handoffs как чат: `🔍 Аналитик → 📐 Архитектор → 🔧 Разработчик` |
| **📝 Задача** | Полное содержимое TODO в отрендеренном markdown |
| **📊 События** | События пайплайна (запуски стадий, завершения, сигналы) |

- **TODO timeline** сверху: `[✅ TODO-0001] ─ [✅ TODO-0002] ─ [🔄 TODO-0003]`
- **Чип пайплайна** рядом с TODO: пайплайн, стадии которого реально нарисованы (забег, закреплённый на нестандартном пайплайне, показывает свои стадии, а не дефолтные)
- **Статус воркера** в sidebar: PID, CPU, последняя строка лога
- **Браузерное уведомление** когда verify готов
- **Таймер** от запуска первого агента, замораживается на verify

## Pre-dispatch проверка

Перед запуском пайплайна awf грепает код на ключевые слова из TODO. Если паттерн уже в коде:

```
⚠️ Pre-check: 'days_in_period' найден в 3 файлах.
Задача может быть уже реализована — проверьте перед запуском.
```

Это предотвращает пустые прогоны пайплайна для уже выполненных задач.

## Батчинг задач

Supervisor группирует BACKLOG задачи по глубине пайплайна:

- **1-2 стадии:** небольшие TODO (один фикс)
- **3-5 стадий:** группировать задачи (цель — 10+ строк реальных изменений)
- **6+ стадий:** крупные инкременты (целая фича)

**Правило:** не запускать 5-агентный пайплайн для однострочного фикса. Объединяйте задачи.

## Восстановление после сбоев

| Ситуация | Что происходит |
|---|---|
| Воркер не просигналил (нет DONE/BLOCKED) | Salvage — awf пишет SALVAGE промт, supervisor решает |
| Процесс пайплайна упал | `awf_continue` — возобновляет с последней контрольной точки |
| `awf_kill` во время работы воркера | Kill гасит стадию ВМЕСТЕ С воркером (его группу процессов). Ответ называет pid пайплайна и воркера; переживший воркер — громкое предупреждение с pid. Следующий `awf_start`/`awf_continue` предупреждает о живом осиротевшем воркере от прошлого kill — его правки легли бы в новую единицу. CLI-двойник (рекавери без MCP): `python3 -m awf kill --project-dir <path>` — тот же API, то же поведение |
| Orphan TODO (провален dispatch) | Не очищается автоматически. Удалить: `awf_reset(orphans=True)` |
| Коммит провален (pre-commit hook) | TODO НЕ архивируется, изменения остаются для ручного ревью |
| Supervisor завис на verify >1 ч | Стадия таймаутится → salvage. Увеличить: `AWF_SUPERVISOR_TIMEOUT=7200` (env) или `awf start --timeout 7200` |

## Где что лежит

```
.agentic/
├── config.yaml              # Конфиг проекта (роли, модели, пайплайн)
├── pipelines/default.yaml   # Определение стадий пайплайна
├── roles/                   # Файлы ролей (supervisor.md, роли воркеров)
├── doctrine/                # Уроки проекта (U9) — подставляются в промпт каждой роли
├── phases/plan.md           # План проекта — шаги с [x]-отметками
├── inbox/                   # TODO файлы + сигналы dispatch
├── outbox/                  # Сигналы воркеров (DONE, BLOCKED, REVIEW)
├── handoff/                 # Handoff файлы по стадиям (создаётся при dispatch)
├── context/                 # Базелины (SHA, тесты, окружение)
├── logs/                    # orchestrator.log, вывод воркеров
├── inputs/                  # Субмиты форм (создаёт плагин)
├── done/{todo_id}/          # Архив завершённых TODO
├── state/current.yaml       # Состояние пайплайна (stage, todo, PID, phase)
├── state/run.yaml           # Состояние забегов, если активен
└── state/dashboard_port     # Порт HTTP-сервера дашборда
```

## Все tools (справочник)

45 инструментов: 40 `awf_*` workflow + 5 UI (формы).

### Lifecycle
| Tool | Что делает |
|---|---|
| `awf_init` | Создаёт `.agentic/`, определяет стек, возвращает промт фазы |
| `awf_status` | Активные TODO, состояние пайплайна, инфо о стадии |
| `awf_brief` | RUN4 #1: карточка погружения/восстановления — живое состояние, карта инструментов, ритуалы, рецепты |
| `awf_report` | Статусы задач + git diff + последний лог тестов |
| `awf_reset` | Очистка runtime (tasks_only / full / orphans) |

### Pipeline
| Tool | Что делает |
|---|---|
| `awf_start` | Запуск пайплайна (background), дашборд открывается |
| `awf_continue` | Возобновление прерванного пайплайна — ack пинит свою единицу; для явного пина — `todo_id` |
| `awf_kill` | Остановка пайплайна **и воркера стадии** (его группа процессов) — ответ называет оба pid; переживший воркер — предупреждение с pid |
| `awf_retry_stage` | Kill + retry со salvage-стадии — перезапускает именно salvage-единицу (TODO закреплён, не «самый свежий активный») |
| `awf_write_pipeline` | Записать именованный пайплайн по стадиям (config/supervisor не трогает) |
| `awf_pipelines` | Список пайплайнов в `.agentic/pipelines/` + активный |

**Пропуск чекпоинта на один запуск (RUN3 #6).** `awf_start` / `awf_continue`
принимают `no_checkpoints=true` — форма BD-36 пропускается только для этого
запуска. Флаг живёт время процесса: в config и state не пишется, следующий
запуск спросит снова (run-флаг `awf_run_start(no_checkpoints=...)` работает
как раньше).

**Пин движка (TODO-0077).** Когда проект — сам awf (или движок не должен
импортировать рабочее дерево: `python -m awf` ставит cwd первым в
`sys.path`), в `.agentic/config.yaml` задают `automation.runner_dir` —
каталог с `awf/__init__.py`. Фоновый ребёнок `awf_start` / `awf_continue`
запускается из этого закреплённого чекаута; `--project-dir` и остальной
argv ребёнка не меняются. Значение проверяется до спавна (неверный путь →
`AwfApiError`, процесс не создаётся, PID-файл не пишется). Без ключа
поведение не меняется (`cwd` = каталог проекта).

**Именованные пайплайны** (RUN3 #1). Несколько пайплайнов в одном проекте,
запуск нужного по имени:

```console
$ awf pipeline-write audit-llm --role agent-implementer
Wrote pipeline 'audit-llm' (3 stages) → .agentic/pipelines/audit-llm.yaml
$ awf pipelines
  audit-llm
* default  (active)
$ awf start --pipeline audit-llm
```

- `awf pipeline-write <name> --role R1 [--role R2] [--force]` (MCP
  `awf_write_pipeline`) пишет ТОЛЬКО `.agentic/pipelines/<name>.yaml` —
  стадии генерируются как в setup-форме (plan → роли → verify);
  config.yaml и supervisor.md не трогаются.
- `awf pipelines` (MCP `awf_pipelines`) — список файлов + активный
  (`default_pipeline` из config.yaml).
- Неизвестное имя в `--pipeline` (или `awf_start(pipeline=...)`) — внятная
  ошибка со списком доступных; молчаливого запуска `default` нет.
- `awf status` показывает активный пайплайн и число доступных.

**`awf_unblock`** (CLI `awf unblock`). Перевыданный TODO остаётся невидимым, пока рядом
лежит старый `BLOCKED-<id>.ready` / `ACK-<id>.ready` — `awf_status` показывает пустой
список, `awf start` отвечает «No active TODO». Unblock переносит эти закрывающие
сигналы (каноническая и legacy-формы) в каталог `context/unblock-<id>-<ts>/` — след
остаётся, TODO снова активен. DONE-закрытия не трогаются: заархивированный TODO
возвращает только `awf restore`. `awf_dispatch_todo` сам снимает stale BLOCKED/ACK
при перевыдаче того же номера и отказывается перевыдавать номер, чьё DONE-закрытие
ещё лежит в outbox.

**`awf_todo_remove`** (CLI `awf todo-remove`). Убирает TODO, который никогда не
стартовал — нет dispatch-`.ready`, сигналов и прогресса. Файл переносится в
`done/<id>/removed-<timestamp>.md`, след остаётся. Если есть `.ready` или любой
сигнал/прогресс — отказ с подсказкой `awf unblock` / `awf reset --orphans`.

**`awf_todo_retire`** (CLI `awf todo-retire TODO-NNNN --reason "…"`). Reject-путь
пишет в outbox `DONE-<id>.{md,json}`, но НЕ сигнал `DONE-<id>.ready` — из-за этого
отклонённый TODO вечно «активен» в `awf status` (нет закрытия, нет архива). Retire
переносит файлы TODO (`TODO-<id>.md`, `.ready`, `PROGRESS-*`, `DONE-*.md/.json` без
`.ready`, `REVIEW-*`) в `done/<id>/` и пишет `done/<id>/RETIRED-<timestamp>.md` с
причиной, кем и когда — без фейкового DONE-сигнала. Отказы: нет файла TODO ни в inbox,
ни в `done/`; уже архивирован (`done/<id>/TODO.md`); живой пайплайн на этом id
(`awf kill` или дождаться); пустая `--reason` (обязательна). `awf restore` по-прежнему
возвращает retired-TODO.

**`awf_todo_update`** (CLI `awf todo-update TODO-NNNN --content-file <path> |
--content "…"`). Переписать текст TODO, который НЕ стартовал: содержимое
`inbox/TODO-<id>.md` заменяется на месте, а номер, dispatch-`.ready` и baseline
остаются нетронутыми (baseline фиксирует git sha, не текст). Прежнее содержимое
бэкапится побайтово в `context/TODO-<id>.md.bak-<timestamp>`; `--reason` пишется в
лог оркестратора. Отказы: нет файла TODO в inbox; пустой content; TODO уже стартовал
(любой сигнал в outbox, `ACK-`/`APPROVE-` в inbox или непустой `PROGRESS` — юнит в
работе: править через REVIEW/replan либо retire + перевыпуск); живой пайплайн на этом
id.

**Untracked-файлы и коммит юнита (RUN10 #4).** Коммит-гейт коммитит только
изменения с baseline юнита — файл, который лежал untracked ДО dispatch, не
является работой юнита, поэтому по замыслу исключается из его коммита. Эта
защита раньше была невидимой, теперь она видна:

- `awf_dispatch_todo` в ответе выдаёт предупреждение со списком pre-existing
  untracked, которые НЕ попадут в коммит юнита (кап 10, остальные как
  «…ещё N»; строки нет, когда дерево чистое).
- у `awf_verify_pack` есть информационная секция `untracked_excluded` с тем
  же списком — pass, не fail: исключение — нормальное поведение.
- чтобы осознанно включить pre-existing файл, dispatch с
  `awf_dispatch_todo(..., include_untracked=["docs/notes.md", ...])` (MCP).
  Каждый путь должен существовать, быть untracked, не gitignored и оставаться
  внутри проекта; любой невалидный путь отклоняет dispatch до любых
  побочных эффектов (ни TODO, ни baseline). Включённые пути traced в
  `.agentic/context/BASELINE-<id>.include` и попадают в коммит юнита.

**Пайплайн на элемент (RUN3 #2).** Очередь принимает объекты
`{"todo_id": "TODO-0023", "pipeline": "audit-llm"}` рядом со
строками-идами (смешанно); пустой/отсутствующий `pipeline` = пайплайн из
config. `awf_dispatch_todo(..., pipeline=...)` пишет имя во front-matter
TODO, и `awf_run_next` читает его для элементов без пайплайна на уровне
очереди. Неизвестное имя отказывает запуску со списком доступных
пайплайнов (RUN3 #1).

**Долгие ожидания.** Один вызов `awf_wait_for_event` рвётся по потолку
одиночного ожидания — 55 с по умолчанию, поднимается через
`wait.cap_seconds` в `.agentic/config.yaml` (или env `AWF_WAIT_CAP` — он
приоритетнее). Дефолтные 55 с — это потолок самого инструмента, НЕ
транспорта: поднятый mcp timeout в opencode.json его не поднимает.
Инструмент говорит об этом в каждом `next_action` и называет точную ручку:
пока потолок дефолтный — советует `wait.cap_seconds: <T>` / `AWF_WAIT_CAP=<T>`
(T = твой mcp timeout `agent-workflow-ui` из opencode.json минус ~30 с, если
читается). Совет «подними mcp timeout в opencode.json» появляется только
пока этот таймаут неизвестен или меньше потолка — и никогда, когда потолок
поднят в конфиге или env; `suggested_timeout` при этом следует твоему
потолку (без истории стадий: ~90% от него, 55 → 55, 600 → 540).

**Подсказки по режиму (RUN10 #1).** Подсказки в ответах
`awf_wait_for_event` / `awf_approve` зависят от режима. При активном забеге:
таймаут предлагает следующий вызов цикла
(`awf_wait_for_event(timeout=<suggested>, actionable_only=True)`), а шаг
после approve — `awf_run_next`; «жди пользователя» — только когда забега
НЕТ. Во время забега фаза показывается как `run` (не `done` прошлого
цикла), а событие `done` в забеге отдаётся только если текущий элемент
забега реально завершён (архив/коммит) — смерть пайплайна посреди
итерации оставляет ожидание (timeout/idle).

**Полномочия супервизора.** Реплан, переписывание ТЗ и сплит задачи — штатная
опция супервизора, approve владельца не требуется. Эскалация владельцу —
только стоп-лист: дважды отвергнутая итерация, BLOCKED без решения, бюджет,
аудит-точка. Причина replan/сплита фиксируется в отчёте/ноте забега.

**Роль из opencode-скилла** (RUN3 #3) — одной командой вместо рукописного
файла. Роль получает тело SKILL.md (YAML front-matter скилла вырезан) под
комментарием-провенансом с путём к источнику и датой. Скиллы проекта
(`.opencode/skills/`) ищутся раньше глобальных
(`~/.config/opencode/skills/`); имя роли по умолчанию — имя скилла;
занятое имя файла роли — отказ без `--force`:

```console
$ awf add-role security-audit --from-skill agent-security-auditor
Created: ./.agentic/roles/security-audit.md
  (content copied from skill 'agent-security-auditor')
```
